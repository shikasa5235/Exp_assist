# 露出アシスト — 写真を使った測定機能 仕様書

**位置づけ：** `docs/exposure-app-spec.md` への拡張仕様。3つの独立した機能を扱う。

**この文書の読み方：** §1 が成立性の全体像、§2 が判断の分かれ目、§3〜§5 が各機能の仕様、
§9 が段階分けと検証計画。実装前に §1・§2・§9.1 を必ず読むこと。

---

## 1. 3つの機能と成立性

| 機能 | 撮影に使う機材 | 成立 | 価値 |
| --- | --- | --- | --- |
| **A. スマホを露出計にする（シーンEV測定）** | スマホ | ○ | **最大。§3** |
| **B. カメラの EXIF で校正の入力を補完** | カメラ | ○ | 中。§4 |
| **C. 白飛びの予測（ハイライト測定）** | スマホ | △ | 目安として。§5 |
| ~~D. スマホでストロボ発光を撮る~~ | スマホ | ✗ | 不可能。§2.1 |
| ~~E. グレーカードでストロボ校正~~ | カメラ | △ | **低。§5.4 で見送り** |

**A が本命です。** 当初の依頼（ストロボ校正）より価値が大きく、かつ堅牢です。

---

## 2. 判断の分かれ目：発光を捉える必要があるか

### 2.1 発光を捉える必要がある場合はスマホでは不可能

ストロボの発光は 1/250〜1/9000 秒で終わる。スマホのシャッターを
その瞬間に合わせる手段がないため、発光を写せない。

**したがってストロボ校正にスマホのカメラは使えない。**

### 2.2 発光を捉える必要がなければスマホで問題ない

**アンビエント光（定常光）の測定は同期を必要としない。**
スマホのカメラは自動露出でシーンを測光し、選んだ F値・SS・ISO を EXIF に記録する。
その3つの数値から逆算すれば、**シーンの明るさ（EV）が求まる。**

これは露出計そのものの原理である。

そして日中シンクロで最も重要な入力は**シーンEV**であり、
現在はシーンチップ（±1段の目安）＋微調整スライダーで手動指定している。
ここが実測に置き換わる。

## 3. 機能A：スマホを露出計にする

### 3.1 原理

EXIF の3つの値から EV を求める。

```
EV(ISO100基準) = log2(N² / t) − log2(S / 100)

  N = FNumber
  t = ExposureTime（秒）
  S = ISO
```

**計算例**（F1.8 / 1/1600秒 / ISO40 で撮れた場合）

```
log2(1.8² × 1600) = log2(5184)  = 12.34
log2(40 / 100)    = log2(0.4)   = −1.32
EV = 12.34 − (−1.32) = 13.66
```

この値をシーンEV としてアプリに取り込む。

### 3.1.1 EXIF の値を 1/3段グリッドへ寄せないこと（フェーズ0 で確定）

**当初「`exactGear()` と同じ変換が必要」と書いていたが誤り。** 実機の EXIF は連続値だった。

| タグ | 実機の値 | 1/3段グリッド上か |
| --- | --- | --- |
| `ExposureTime` | **1/4405** | **無い**（2^-12.105） |
| `FNumber` | 1244236/699009 = 1.7799999713880652 | ほぼ F1.8 だが厳密には別 |
| `FocalLength` | 251773/37217 = 6.764999865652793 | — |

**スマホの AE は連続値でシャッターを制御し、実測値をそのまま記録している。**
`1/4000` や `1/5000` にスナップすると、**最大 1/6段 の誤差を自分で作り込む。**

| 対象 | 値の性格 | 変換 |
| --- | --- | --- |
| **フェーズ1（スマホ）** | 実測値 | **しない** |
| **フェーズ2（カメラ）** | 公称ラベル（F11・1/250） | **する**（`exactGear()` と同じ） |

ISO 80 は厳密には 79.37（= 100·2^(-1/3)）で 0.011段のずれがあるが、
**一貫性のため ISO も変換しない。** このずれは AE オフセットの校正で吸収される。

`compute()` 入口の `exactGear()` とは逆向きの方針だが、**対象が違うだけで矛盾していない。**
サニー16 の検算（1/125 → 1/128）が意味を持つのは、公称ラベルを扱うフェーズ2 だけ。

非対称の境目は `lightmeter.solveAeOffset` にある。**カメラ側だけ厳密値へ直す。**
回帰テストは **L9**（実機の値で EV 14.0905。寄せた実装は 14.0000 になり落ちる）。

### 3.2 AE バイアスと校正（重要）

**スマホの自動露出は「18%グレーに合わせる」わけではない。**
高輝度シーンではハイライトを守るために暗めに、
暗いシーンでは持ち上げ気味に露出を決める。機種と処理によって差がある。

したがって上の計算値には**未知の定数オフセットが乗る。**
経験的には **−0.5 〜 −2段**の範囲に入ることが多い。

**このオフセットは1回測れば以後ずっと使える。**
既存の機材係数 k（ストロボ）と同じ扱いにする。

#### 校正の手順

**カメラの測光値を基準にする。** アプリの目的は「カメラがどう写すか」を
予測することなので、基準はカメラでなければならない。

1. 同じシーンをスマホで撮る
2. 同じシーンをカメラで測光する（A モードで適正になる F値・SS・ISO を読む）
3. 両方の値をアプリに入れる
4. `offset = EV_camera − EV_phone` を保存する

カメラ側の値は手入力でよい。機能B（EXIF読み取り）が使える場合は
カメラのファイルから自動で入れられる。

#### 状態

```
phone.aeOffsetStops : number   // 既定 0
phone.aeCalibrated  : boolean  // 未校正なら「推定値」バッジ
```

未校正のまま使えるが、**「未校正」バッジを出す。**
既存のストロボ校正と同じ表示規則にする（`docs/exposure-app-ui-spec.md`）。

### 3.3 精度

| 状態 | 精度 |
| --- | --- |
| 未校正 | ±2段（オフセット不明のため） |
| 校正済み・同じレンズ・似たシーン | **±1/3段** |
| 校正済み・レンズ切替（0.5x / 2x） | ±2/3段 |
| 校正済み・大きく異なるシーン（逆光・夜景） | ±1段 |

**校正済みなら現在のシーンチップ（±1段）より正確になる。** ここが価値の本体。

#### 精度を落とす要因

| 要因 | 対処 |
| --- | --- |
| HDR / Smart HDR | **切るのが望ましいが、常に同じ設定なら校正で吸収できる** |
| ナイトモード | 多重露光で EXIF の意味が変わる。切る |
| レンズ切替（超広角・望遠） | F値は EXIF に出るので計算は合うが、AE 傾向が変わる |
| 逆光・極端なコントラスト | AE の判断が変わる。微調整スライダーで補う |

**重要：HDR を切るより「常に同じ設定で使う」ほうが実用的。**
オフセットが安定していれば校正で吸収される。
マニュアルには「校正時と同じ設定で撮る」と書く。

### 3.4 UI

かんたんタブのシーン選択の下に配置する。

```
シーン
［ 16 ］［ 15 ］［ 14 ］［ 13 ］［ 12 ］［ 11 ］…

  または

［ 写真から測る ］   EV 13.7 を測定しました  ［使う］
                     推定値（未校正）
```

- **シーンチップを置き換えない。** 併存させる
- 測定値を使うと、シーンチップの選択が外れ「実測 EV 13.7」と表示される
- 微調整スライダーは引き続き使える（測定値からの補正として機能する）
- 未校正なら「推定値」バッジ

#### 測定できない場合

| 条件 | 表示 |
| --- | --- |
| EXIF が無い | 「この写真には撮影情報がありません。カメラアプリで撮った写真を選んでください」 |
| F/SS/ISO のいずれかが欠損 | 「撮影情報が不足しています」 |
| ナイトモードの疑い（SS が長く ISO が高い） | 「ナイトモードで撮影された可能性があります。値が正確でない場合があります」 |

**黙って値を出さないこと。**

### 3.5 なぜ live camera（getUserMedia）を使わないか

リアルタイムのプレビューから測光する方式は成立しない。

ブラウザの `MediaTrackSettings` で `exposureTime` や `iso` を取得できるのは
一部の Chrome / Android のみで、**Safari は非対応。**
露出設定が分からない画素値は絶対的な明るさを表さないため、露出計にならない。

**静止画の EXIF を読む方式が唯一成立する。**
撮影→選択の2手順が必要になるが、確実である。

## 4. 機能B：カメラの EXIF で校正の入力を補完

当初の依頼にあたる部分。**機能A の校正にも使える。**

### 4.1 得られるもの

| EXIF タグ | 値 | 用途 |
| --- | --- | --- |
| `FNumber` (0x829D) | F値 | ストロボ校正の必須入力／EV |
| `ExposureTime` (0x829A) | SS | 同調速度との整合検証／EV |
| `ISOSpeedRatings` (0x8827) | ISO | ストロボ校正の必須入力／EV |
| **`ExposureBiasValue` (0x9204)** | **露出補正（段）** | **EV に加算する。必須（下記）** |
| `FocalLength` (0x920A) | 焦点距離 | 参考表示 |
| **`FocalLengthIn35mmFilm` (0xA405)** | **35mm換算焦点距離** | **AE 校正時と別レンズかの判定** |
| `Flash` (0x9209) | 発光の有無 | 整合検証 |
| `Make` / `Model` | 機種名 | 校正履歴 |
| `DateTimeOriginal` | 撮影日時 | 校正履歴 |

**得られないもの：ストロボ→被写体の距離、マニュアル発光量、モディファイア。**
これらは手入力のまま残る。

#### `ExposureBiasValue` は必須（0x9204・SRATIONAL）

スマホで露出補正をかけた写真を使うと、その分 EV がずれる。**EV の式に含める。**

```
EV = log2(N²/t) − log2(S/100) + exposureBias + aeOffsetStops
```

0 以外なら注記も出す：「露出補正 +0.7 の写真です。補正なしで撮ると精度が上がります」。
**負値があるので符号付き有理数（SRATIONAL）として読むこと。** 回帰テストは **E10**。

#### `FocalLengthIn35mmFilm` の用途（0xA405）

iPhone はレンズが複数あり（超広角13mm・主24mm・望遠120mm相当）、AE の傾向が異なりうる（§3.3）。
**レンズごとにオフセットを持つのは過剰なので注記だけ。**

AE 校正時に `phone.aeCalFocal35` として保存し、測定時の値と **1.5倍以上** 離れていたら
「校正時と別のレンズで撮影されています（校正 24mm / 今回 13mm）。精度が落ちる可能性があります」。

#### 読まないタグ

| タグ | 理由 |
| --- | --- |
| `BrightnessValue` (0x9203) | **Apple の値は APEX の関係式から 0.8段ほどずれることが知られている。** EV は F/SS/ISO から計算する |
| `GPSInfo` (0x8825) | §6.5。ポインタを追わない・保存しない・返さない |

`js/exif.js` の読むタグは `TAG` テーブル1箇所に集約してある。**この2つをそこに足さないこと。**
回帰テストは **E7**（返り値に GPS 由来のキーが無い）。

### 4.2 価値

現在のストロボ校正は4項目すべて手入力で、**F値と ISO の転記ミスが k を直接歪める。**
実際に「1/1」のパース不具合で校正が失敗していた経緯がある。
EXIF から取れば入力誤りが構造的に消える。

### 4.3 整合検証

| 検証 | 条件 | 警告 |
| --- | --- | --- |
| 同調速度 | `ExposureTime` < 同調速度 かつ発光あり | 「SS 1/500 は同調速度 1/250 より速いため、通常発光では同期しません。HSS で撮影しましたか」 |
| 発光の有無 | `Flash` が非発光 | 「この写真ではストロボが発光していません。校正には使えません」 |
| 手入力との差 | 手入力 F値 と EXIF が不一致 | 両方を並べて「EXIF は F11、入力は F8 です。どちらを使いますか」 |

**3つ目が実用上いちばん効く。** 転記ミスをその場で気づける。

### 4.4 校正履歴

`DateTimeOriginal` と `Model` を校正値と一緒に保存する。

```
オクタ60cm        k = 2.41   2026-08-03  ILCE-7M4
標準リフレクター  k = 2.33   2026-07-30  ILCE-7M4
```

校正値は実測でしか得られない資産（`docs/MAINTENANCE.md` §9）なので、
出所が残るのは保守上の価値がある。

## 5. 機能C：白飛びの予測

**「日中シンクロで背景が白飛びする」という実運用の課題への対応。**
遊びの範囲として実装する前提で、精度の限界を明示する。

### 5.1 何が問題なのか

日中シンクロで背景が飛ぶ原因は3つある。

| 原因 | 現在のアプリで防げるか |
| --- | --- |
| シーンEV の見積もり違い | **機能A で解決する** |
| 背景段数の選択が明るすぎる（0 や +1） | 選択は自由。警告なし |
| シーンのダイナミックレンジがセンサーを超える | **判定していない** |

3つ目が本質的な難しさである。**適正露出でも空は飛ぶ。**
中間調から上のヘッドルームは JPEG で約3段、RAW でも 3.5〜4段しかない。
晴天の空が被写体より4段明るければ、被写体を適正にした時点で空は飛ぶ。

### 5.2 測って何を出すか

**「空が何段明るいか」という数値を出すのではなく、
「背景を何段まで落とせば空が残るか」を出す。**

```
測定：空が被写体より 4.2段 明るいようです（目安）

  背景 0段   → 空は約 1.2段 オーバー。飛びます
  背景 −1段  → 空は約 0.2段 オーバー。ぎりぎり
  背景 −2段  → 空が残ります   ← 推奨

  ※ 空を飛ばす表現を狙う場合はこの警告を無視してかまいません
```

**段数そのものを見せるより、選ぶべき背景段数を出すほうが実用的。**
誤差に強く、そのまま行動に移せる。

### 5.3 測定の限界

**精度は ±1.5段程度。** 理由は3つある。

| 要因 | 影響 |
| --- | --- |
| **HDR のトーンマッピング** | 空を圧縮して記録するため、実際より暗く測れる。最大の誤差要因 |
| トーンカーブの S 字 | ハイライト域で画素値と段数の対応が崩れる |
| 空が既に飛んでいる | V=255 に張り付いていると何段オーバーか測れない |

**HDR を切って撮ることを案内する。** それでもショルダーは残る。

#### 中間調での対応関係（sRGB ガンマ、18%グレー基準）

| 適正からのずれ | 線形値 | 画素値（0-255） |
| --- | --- | --- |
| −2段 | 0.045 | 60 |
| −1段 | 0.090 | 84 |
| **±0段** | **0.180** | **118** |
| +1段 | 0.360 | 162 |
| +2段 | 0.720 | 222 |
| +2.5段 | 1.000 | 255（飽和） |

1段あたり画素値が約1.37倍。**+2.5段で飽和して測定不能になる。**

### 5.4 測らない代替案（先に検討する価値がある）

**写真を使わずに同じ警告を出せる可能性がある。**

アプリは既にシーンEV と背景段数を知っている。
そこに「シーン別のコントラスト目安」と「センサーのヘッドルーム」を加えれば、
測定なしで警告が出せる。

| シーン | 空と被写体の差（目安） |
| --- | --- |
| 快晴・順光 | 2.5段 |
| 快晴・逆光 | 4.5段 |
| 晴れ・日陰の被写体 | 4段 |
| 曇り | 1.5段 |

```
ヘッドルーム（JPEG）= 3段 と仮定
警告条件：コントラスト目安 + 背景段数 > 3
```

**コード量は20行程度。** 機能C の 150行と比べて費用対効果が高い。

**推奨：まず §5.4 の表方式で警告を出し、
それで不足を感じてから §5.2 の測定に進む。**

測定方式は「実測」を名乗る割に ±1.5段なので、
表方式（±1段程度の目安）と大差ない可能性がある。

### 5.5 見送る機能：グレーカードによるストロボ校正

当初の仕様案にあった「カメラの写真の明るさからストロボ校正のずれを測る」機能は
**見送る。**

理由は3つ。

- ストロボ校正は機材とモディファイアの組み合わせごとに一度で済む作業で、頻度が低い
- 機能B（EXIF自動入力）で転記ミスが消えれば、残る誤差は主にユーザーの適正判断のみ
- グレーカードを持ち歩く前提は、屋外・片手という利用条件に合わない

必要になれば §5.3 の測光アルゴリズムを流用できる。

## 6. ファイル形式の扱い

### 6.1 実機の結果：HEIC は届かない（フェーズ0 で確定）

**iPhone 16 Pro Max / iOS 26.1 / カメラ設定「高効率」（HEIC）** で検証した結果：

| 見たもの | 結果 |
| --- | --- |
| `File.type` | `image/jpeg` — **iOS が選択時に変換している** |
| EXIF | **完全に残存** |
| 読めたタグ | 主要8タグすべて |
| EV | 14.09（検算一致） |
| GPS | 存在するが読まない（意図どおり） |

**カメラ設定が「高効率」のままでも `<input type="file">` には JPEG で届く。**
当初「機能A が主機能になるので HEIC 対応が必須」と書いたが、**前提が誤っていた。**

したがって **BMFF パースも「互換性優先にしてください」の案内も、通常経路では不要。**

### 6.2 HEIC の扱い：検出して案内するだけ

iOS のバージョンや経路によって挙動が変わる可能性があるため、**退避だけ残す。**

```js
// js/exif.js は先頭バイトで判定して format を返すだけ。**パースしない**
if (exif.format === 'heic') {
  // 「設定 → カメラ → フォーマット → 互換性優先 に変更すると読み取れます」
}
```

**BMFF パースを実装しないこと。** 5行の退避で足りる。
実際にここへ到達したという報告が出るまで、100〜150行のパーサを持つ理由がない。

回帰テストは `tests.html` の **E8**（HEIC の先頭バイトで `format: 'heic'`、値は `null`）。

### 6.3 対応形式

| 形式 | EXIF | 画素の展開（機能C） |
| --- | --- | --- |
| JPEG | ○ APP1 | ○ 全ブラウザ |
| HEIC | △ BMFF パース（フェーズ2） | Safari のみ |
| PNG | ✗ 通常削除される | ○（EXIF なしなので機能A は不可） |
| RAW | ✗ 対象外 | ✗ |

**RAW は対象外。** Canvas がデコードせず、EXIF 構造がメーカーごとに異なる。
依存パッケージゼロの制約下では現実的でない。

### 6.4 iOS の写真アプリ経由での EXIF 保持

**これが最大の未知です。** `<input type="file">` で写真アプリから選択したとき、
iOS が EXIF を保持するか再エンコードするかが分かっていない。

**機能A と機能B の両方がここに依存する。** 実装前に検証する（§9.1）。

EXIF が失われる経路がある場合、「ファイル」アプリから選ばせる誘導が必要になる。

### 6.5 GPS 情報は読まない

EXIF には GPS タグ（0x8825）が含まれ得る。

**GPS タグは読み取らない。保存しない。表示しない。**
パーサの実装から意図的に除外し、その旨をコメントに書く。

このアプリは通信しない設計であり、位置情報を扱う理由がない。

## 7. アーキテクチャ

既存の純粋関数／副作用の分離を崩さないこと。

```
js/exif.js        [純] ArrayBuffer → EXIF値オブジェクト
js/lightmeter.js  [純] EXIF値 + オフセット → シーンEV
js/photometry.js  [純] 画素配列 → 明るさの段数（機能C・フェーズ4）
js/ui.js               ファイル選択・Canvas 描画・上記の呼び出し
js/compute.js          既存の計算（シーンEV の入力元が増えるだけ）
```

### 7.1 `js/exif.js`（純粋関数）

```js
/**
 * @param {ArrayBuffer} buf 画像ファイル全体
 * @returns {{
 *   format: 'jpeg'|'heic'|'png'|'unknown',
 *   fNumber: number|null,
 *   exposureTime: number|null,   // 秒（1/250 なら 0.004）
 *   iso: number|null,
 *   focalLength: number|null,
 *   flashFired: boolean|null,
 *   make: string|null,
 *   model: string|null,
 *   dateTimeOriginal: string|null,
 * }|null}
 */
export function parseExif(buf) { … }
```

- **DOM・Canvas・fetch・localStorage に触らない**
- 読めなければ `null`。例外を投げない
- リトルエンディアン（`II`）とビッグエンディアン（`MM`）の両方に対応
- GPS タグを読まない（§6.5）

### 7.2 `js/lightmeter.js`（純粋関数）

```js
/**
 * EXIF の露出3値からシーンEV（ISO100基準）を求める
 * @returns {{ ev: number|null, reason: string|null, suspectNightMode: boolean }}
 */
export function evFromExposure({ fNumber, exposureTime, iso }, aeOffsetStops) { … }

/**
 * スマホとカメラの測定値から AE オフセットを求める
 * @returns {{ offsetStops: number|null, reason: string|null }}
 */
export function solveAeOffset(phoneExposure, cameraExposure) { … }
```

**式が単純なので純粋関数として切り出す価値がある。**
テストで数値を固定でき、退行を検出できる。

### 7.3 `js/photometry.js`（フェーズ4のみ）

```js
/**
 * @param {{width:number, height:number, data:Uint8ClampedArray}} img
 * @param {{x:number, y:number, w:number, h:number}} region 相対座標 0-1
 * @returns {{ stops:number|null, reliable:boolean, reason:string|null, … }}
 */
export function measureRegion(img, region) { … }
```

**ImageData そのものではなく同形のプレーンオブジェクトを受け取る**ことで、
テストで合成データを渡せるようにする。

## 8. 受け入れテスト

### 8.1 `exif.js`（合成バイト列で検証）

**画像ファイルをリポジトリに置かない。** テスト内で `Uint8Array` を組み立てる。

| # | 内容 |
| --- | --- |
| E1 | リトルエンディアン（`II`）の JPEG APP1 から F値・ISO を読める |
| E2 | ビッグエンディアン（`MM`）でも同じ値 |
| E3 | `FNumber` が有理数（1100/100）で 11.0 になる |
| E4 | `ExposureTime` が 1/250 の有理数で 0.004 になる |
| E5 | EXIF なしの JPEG で `null`、例外を投げない |
| E6 | 壊れたバイト列で `null`、例外を投げない |
| E7 | GPS タグを含む EXIF から、GPS を含まない結果を返す |
| E8 | HEIC の先頭バイトで `format: 'heic'` を返す |
| E9 | RAW（未知の先頭バイト）で `format: 'unknown'` |

**E5・E6・E9 が重要。** 読めないファイルで壊れないこと。

### 8.2 `lightmeter.js`

| # | 入力 | 期待 |
| --- | --- | --- |
| L1 | F1.8 / 1/1600 / ISO40 / オフセット0 | EV ≈ 13.66 |
| L2 | F16 / 1/125 / ISO100 / オフセット0 | EV ≈ 15.0（サニー16の検算） |
| L3 | F1.8 / 1/1600 / ISO40 / オフセット+1.3 | EV ≈ 14.96 |
| L4 | ISO が null | `ev: null` と理由 |
| L5 | ExposureTime が 0 | `ev: null`（ゼロ除算を起こさない） |
| L6 | SS 1秒以上 かつ ISO 3200以上 | `suspectNightMode: true` |
| L7 | スマホ EV 13.66・カメラ EV 15.0 | `offsetStops ≈ 1.34` |
| L8 | `solveAeOffset` に欠損値 | `offsetStops: null` と理由 |

**L2 がサニー16の検算になる。** `log2(256 × 125) = log2(32000) = 14.97`。
式が正しいことをここで固定する。

### 8.3 統合

| # | 内容 |
| --- | --- |
| I1 | 測定 EV がシーンEV として `compute()` に流れ、日中シンクロの結果が変わる |
| I2 | 未校正のとき `phone.aeCalibrated` が false で、バッジ用のフラグが立つ |
| I3 | EXIF の F11・ISO100 と距離3m・発光量1/1 から k = 2.33 が求まる（機能B） |
| I4 | `ExposureTime` が同調速度より速く発光ありのとき、警告が返る（機能B） |

### 8.4 `photometry.js`（フェーズ4のみ）

| # | 内容 |
| --- | --- |
| P1 | V=118 一様 → `stops ≈ 0`、`reliable: true` |
| P2 | V=162 一様 → `stops ≈ +1.0` |
| P3 | V=84 一様 → `stops ≈ −1.0` |
| P4 | V=255 が範囲の 50% → `reliable: false`、理由は飽和 |
| P5 | V=0 が範囲の 50% → `reliable: false`、理由は黒潰れ |
| P6 | `stops` が +2.0 相当 → `reliable: false` |
| P7 | 市松模様 → `reliable: false`（標準偏差） |
| P8 | 範囲が画像外にはみ出しても例外を投げない |

## 9. 段階分けと検証計画

### 9.1 フェーズ0：EXIF が読めるかの検証（最初にこれをやる）

**§6.4 の未知が解決するまで実装に着手しない。**
機能A と機能B の両方がここに依存する。

使い捨ての検証ページ `tools/exif-probe.html` を1枚作り、実機で確認する。

**確認する経路**

| # | 経路 | 見るもの |
| --- | --- | --- |
| 1 | **iPhone のカメラで撮影 → 写真アプリ → 選択** | **機能A の主経路。EXIF が残るか。形式は HEIC か JPEG か** |
| 2 | iPhone のカメラで撮影 → ファイルアプリ → 選択 | 同上（代替経路） |
| 3 | カメラ → AirDrop → 写真アプリ → 選択 | 機能B の主経路 |
| 4 | カメラ → AirDrop → ファイルアプリ → 選択 | 同上（代替経路） |
| 5 | PC でカメラの JPEG を直接選択 | **対照実験。ここで読めなければパーサの不具合** |
| 6 | 設定を「互換性優先」にして 1 を再試行 | JPEG になるか |

**5 を最初にやること。** 経路の問題とパーサの不具合を切り分けられる。

**この検証は30分程度で終わる。**
飛ばして実装すると、数百行書いたあとに成立しないことが判明する可能性がある。

**判断**

| 結果 | 次の行動 |
| --- | --- |
| どの経路でも EXIF が残る | フェーズ1 へ |
| 写真アプリ経由で失われる | フェーズ1 へ。ファイルアプリへ誘導する UI を追加 |
| どの経路でも失われる | **機能A・B ともに成立しない。** §12 を読んで是非を再検討 |
| HEIC のまま渡される | 「互換性優先」の案内で回避（§6.2）。それでも残るなら BMFF パースが必要 |

### 9.2 フェーズ1：`exif.js` ＋ 機能A（スマホ露出計）

**主機能。ここまでで価値の大半が得られる。**

- `js/exif.js`（JPEG のみ。HEIC は検出して案内）
- `js/lightmeter.js`
- テスト E1〜E9・L1〜L8・I1・I2
- かんたんタブの「写真から測る」
- AE オフセットの校正 UI（カメラの測光値は手入力）
- 未校正バッジ

### 9.3 フェーズ2：機能B（校正の入力補完）

**小さい。`exif.js` が済んでいれば UI の追加が主。**

- 設定タブの校正欄に「写真を選ぶ」
- F値・ISO の自動入力と出所バッジ
- 整合検証の警告3件（§4.3）
- 校正履歴への機種・日時の記録（§4.4）
- テスト I3・I4
- **機能A の AE オフセット校正で、カメラ側の値も自動入力できるようになる**

### 9.4 フェーズ3：白飛び警告（測らない方式）

**§5.4 の表方式。20行程度。**

- シーン別コントラスト目安のテーブル
- ヘッドルームとの比較で警告
- 「背景を何段まで落とせば空が残るか」の提示

**フェーズ4 に進む前にこれを試すこと。** 測定より費用対効果が高い可能性がある。

### 9.5 フェーズ4：白飛びの測定（任意）

**フェーズ3 で不足を感じた場合のみ。**

- `js/photometry.js`
- テスト P1〜P8
- プレビューとタップによる領域指定
- HDR を切る案内
- **±1.5段の目安であることを明示**

### 9.6 やらないこと

## 10. 配布への影響

### 10.1 追加されるファイル

```
js/exif.js         フェーズ1
js/lightmeter.js   フェーズ1
js/photometry.js   フェーズ4
```

**`sw.js` の `ASSETS` に追加が必須。** `tools/check-sw-assets` が検出する。
`CACHE` のバージョンを上げること（`docs/MAINTENANCE.md` §6.1）。

`tools/exif-probe.html` は ASSETS に入れない（開発用）。

### 10.2 コード量の見積もり

| フェーズ | 内容 | 概算 |
| --- | --- | --- |
| 0 | 検証ページ | 150行（使い捨て） |
| 1 | `exif.js` + `lightmeter.js` + UI | 300〜400行 |
| 2 | 機能B の UI と検証 | 80〜120行 |
| 3 | 白飛び警告（表方式） | 20〜30行 |
| 4 | `photometry.js` + UI | 180〜250行 |

**フェーズ1〜3 で 400〜550行。** 現在の `js/` が約2000行なので2〜3割の増加。
オフラインキャッシュの容量としては問題ない（数十KB）。

### 10.3 外部リソースを増やさないこと

EXIF ライブラリ（exif-js, piexifjs 等）を使わない。
**依存パッケージゼロ、外部リソースゼロが配布要件**（`CLAUDE.md` の不変条件）。

手書きになるが、必要なタグは8個なので現実的な規模に収まる。

### 10.4 プライバシー

```
写真は端末内で読み取るだけで、どこにも送信されません。
位置情報は読み取りません。
```

**このアプリは通信しない設計**なので事実として書ける。
マニュアルと UI の両方に記載する。

## 11. リスクと対処

| リスク | 影響 | 対処 |
| --- | --- | --- |
| iOS が EXIF を削除する | 機能A・B が成立しない | §9.1 で先に検証 |
| HEIC が渡される | 機能A が使えない | 「互換性優先」の案内。将来 BMFF パース |

| コード量の増加 | 保守負荷 | 純粋関数に閉じ込め、テストで固定する |
| 巨大な画像で処理が重い | 操作が固まる | 機能C では長辺256pxに縮小 |

## 12. 入れない判断について

### 機能A（露出計）は入れる価値が高い

**シーンEV は日中シンクロの結果を直接左右する入力**であり、
現在は ±1段の目安で指定している。ここが ±1/3段になれば、
背景の明るさが狙いどおりになる確率が上がる。

利用頻度も高い（撮影ごとに使う）。**費用対効果は良い。**

### 機能B（校正補完）は中程度

校正は組み合わせごとに一度で済む作業。ただし `exif.js` が
フェーズ1 で完成しているなら追加コストは小さい（80〜120行）。**入れてよい。**

### 機能C（白飛び）はまず表方式で

**測定方式（フェーズ4）は ±1.5段で、表方式（フェーズ3）の ±1段程度と大差ない。**
20行で済む表方式を先に入れ、実際に使ってみて不足を感じてから
測定に進むのが合理的。

### 中止の判断ポイント

**フェーズ0 の結果次第。** EXIF が読めなければ機能A・B ともに成立しない。
その場合、フェーズ3（表方式の白飛び警告）だけを 20行で入れる、
という選択も十分ありうる。
