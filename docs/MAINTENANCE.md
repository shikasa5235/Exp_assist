## 3. リポジトリ構成と各ファイルの責務

```
/
├─ index.html                アプリ骨格 + SVGシンボル + マニュアル本文HTML
├─ manifest.webmanifest      PWA マニフェスト
├─ sw.js                     Service Worker（プリキャッシュ + キャッシュ優先）
├─ tests.html                受け入れテスト実行ページ
├─ CLAUDE.md                 AI 作業者向けの憲法
├─ css/style.css             全スタイル（トークン定義を含む）
├─ js/
│   ├─ main.js               初期化 + SW 登録のみ
│   ├─ stops.js         [純] 1/3段テーブル生成と丸め
│   ├─ exposure.js      [純] アンビエント露出ソルバー
│   ├─ flash.js         [純] Ws→GN・校正・HSS・閃光時間・距離の逆算
│   ├─ filters.js       [純] ND 組み合わせ探索
│   ├─ advisor.js       [純] 意図別ロジック・警告・代替案
│   ├─ compute.js       [純] compute(state)→derived。上の純粋モジュールを束ねる層
│   ├─ scenes.js        [定] シーンEV・各種係数テーブル
│   ├─ state.js         [純] 既定状態と makeState/clone/mergeDeep（値は保持しない）
│   ├─ wheel.js             横ホイールピッカー（操作用と表示用で共有・状態を持たない DOM 部品）
│   ├─ storage.js            localStorage ラッパー
│   └─ ui.js                 単一 state・DOM 描画・イベント
├─ tools/check-modules       import/export 整合の検査（bash tools/check-modules）
├─ icons/                    PWA アイコン 4種
└─ docs/                     仕様書 4種
```

`[純]` = 副作用ゼロの純粋関数のみ。DOM・`localStorage`・`window` に触らない。
`[定]` = 定数のみ。ロジックを持たない。

**呼び出しの向き：** `ui.js` → `compute.js` → `advisor.js` → `exposure`/`flash`/`filters`/`stops`/`scenes`。
`flash.js` などの計算モジュールは **`compute.js` 経由で使われる**のが原則で、`ui.js` から直接呼ぶのは
`stops`（表示ラベル）と `flash.calibrate()`（校正）だけ。ここを崩すと計算が2箇所に散る。

### 触るときの影響範囲

| ファイル | 変えると影響する先 | 注意 |
| --- | --- | --- |
| `stops.js` | **全計算**（`compute.js` 経由で全画面） | インデックス体系を変えると保存済み `manual.fIndex` 等が無効になる |
| `scenes.js` | 計算結果・マニュアル本文 | 表の数値を変えたらマニュアル §3/§9/§10 の記述も合わせる |
| `advisor.js` | 警告・マニュアルの導線（`compute.js` 経由） | 警告を追加したら `helpId` も必ず付ける（§8） |
| `flash.js` | ストロボ計算・ユーザーの校正値（`compute.js` 経由。例外は `ui.js` の校正呼び出し） | 推定式を変えると**既存の校正値の意味が変わる**（§9） |
| `compute.js` | **結果パネル・3タブの表示すべて** | `derived` の形を変えたら `ui.js` の描画と `tests.html` の統合テストが連動する。タブ分岐は入口の1箇所だけに置く |
| `state.js` | 既定値・保存データ・テストの前提 | 既定値を変えると保存済み state とずれる（§9 のマイグレーション）。`makeState()` は `tests.html` も使う |
| `wheel.js` | 計算タブの操作ホイールと結果パネルのトラック | 両者は同一部品。片方だけ直すと挙動が食い違う |
| `css/style.css` | 全画面 | トークン以外に生の hex を書かない |
| `sw.js` | **更新の配信そのもの** | §6 を必ず読む |
| `index.html` | 全部 + プリキャッシュ対象 | ファイルを追加したら `sw.js` のリストにも足す（§6） |

## 4. 絶対に変えてはいけないこと

`CLAUDE.md` に全文がある。ここでは**変更提案が来たときに却下する根拠**として要点だけ挙げる。

### 配布形態

- **外部リソース参照ゼロ。** 1行の CDN 参照でオフラインが死ぬ。これが最も起きやすい退行
- **すべて相対パス。** GitHub Pages のプロジェクトサイトは `/<repo>/` 配下。`/css/style.css` は 404
- `manifest.webmanifest` の `start_url` と `scope` は `"./"`
- `sw.js` はルート直下（スコープの都合）

### ドメインの物理

これらを壊すと**計算が静かに間違う**。テストが守っているので、赤くなったら実装ではなく理解を疑う。

| 不変条件 | 守るテスト |
| --- | --- |
| SS はストロボ露出に影響しない | #26 |
| ND はアンビエントとストロボの両方に等しく効く | #27 |
| 1/3段への丸めは表示直前の一度だけ | #1〜#9 全般 |
| 表示ラベルと厳密値は一致しない（`15″`の実体は16秒） | #30 |
| 距離は「ストロボ→被写体」であってカメラからではない | — |
| Ws から GN は一意に決まらない（校正前提） | #13, #14 |
| ND経路と HSS経路は両方計算して並べる（自動選択しない） | #21〜#23 |
| 発光量が大きいほど閃光時間は長い | #28, #29 |

### UI

- 通常操作でソフトキーボードを出さない
- 結果パネルはどのスクロール位置でも見えている
- 範囲外入力を拒否せずクランプして通知する
- 入力欄の `font-size` は 16px 以上（下回ると iOS が自動ズームする）

## 5. 開発環境と動かし方

```bash
cd ~/projects/Exp_assist

# ローカルサーバー（Service Worker は localhost なら HTTPS 不要）
python3 -m http.server 8000

# アプリ
open http://localhost:8000/

# テスト
open http://localhost:8000/tests.html
```

**`file://` で開くと動かない。** ES Modules が CORS で拒否される。必ずサーバー経由で開く。

### 実機（iPhone）での確認

| 段階 | 方法 | 制約 |
| --- | --- | --- |
| レイアウト確認 | 同一LANから `http://<PCのIP>:8000/` | Service Worker は動かない（HTTPS でないため） |
| PWA 全機能 | GitHub Pages にデプロイして Safari から開く | push が必要 |

「ホーム画面に追加」と Service Worker は **HTTPS 必須**。ローカルでは検証できない。

### WSL 環境の既知の癖

- **apt は https 必須。** 80番ポートが閉じているため `sources.list` を https に書き換えてある
  （バックアップ：`/etc/apt/sources.list.bak`）。新規パッケージ導入時も同様
- プロジェクトは `/home/` 配下に置く。`/mnt/c/` はファイルI/Oが遅く、Service Worker の検証で待たされる

## 6. Service Worker の更新手順（最重要）

**ここを間違えると、修正がユーザーに永久に届かない。** 最も事故が起きやすい箇所。

### 6.1 何かファイルを変えたら

```js
// sw.js 冒頭
const CACHE = 'expo-v1';   // ← 必ずインクリメントする
```

**バージョンを上げ忘れると、ユーザーの端末は古いキャッシュを返し続ける。**
オフライン優先のキャッシュ戦略なので、ネットワークを見に行かない。修正が届かない。

### 6.2 ファイルを追加したら

```js
const ASSETS = [
  './', './index.html', './css/style.css',
  './js/main.js', './js/stops.js', /* … */
  // ← 新しいファイルをここに追加する
];
```

**追加を忘れると、オンラインでは動くがオフラインで壊れる。**
開発中は常にオンラインなので**気づかない**。これが2番目に多い事故。

### 6.3 リリース時の必須手順

1. `sw.js` の `CACHE` を上げた
2. `ASSETS` に新規ファイルを追加した
3. push 後、**機内モードで全機能を確認**した
4. DevTools → Application → Service Workers で古い SW が削除されているか確認した

### 6.4 更新の見え方（設計として意図している）

- 新しい SW は `waiting` に入るだけで、**自動でアクティブにならない**
- ヘッダーに「新しいバージョンがあります ［更新］」バーを出す
- **押されたときだけ** `skipWaiting()` → `reload()`

**自動リロードを実装しないこと。** 現場で計算中に画面が飛ぶのが最悪の体験。
「すぐ反映されないのは不便だ」という理由で自動化する提案は却下する。

### 6.5 キャッシュを手で消したいとき

```js
// DevTools のコンソールで
caches.keys().then(ks => ks.forEach(k => caches.delete(k)));
navigator.serviceWorker.getRegistrations().then(rs => rs.forEach(r => r.unregister()));
```

その後リロード。開発中に古いコードを掴んで離さないときに使う。

## 7. マニュアル本文の二重管理

マニュアルは**2箇所に存在する。**

| 場所 | 役割 |
| --- | --- |
| `docs/exposure-app-manual.md` | **正典。** 原稿・レビュー対象 |
| `index.html` 内の `<div id="manual">` | 写し。実際にユーザーが読むもの |

ビルドステップがないため自動同期できない。**運用ルールで担保する。**

### 変更手順

1. `docs/exposure-app-manual.md` を直す
2. `index.html` の該当セクションに反映する
3. `<a id="help-xxxx">` のアンカーが消えていないか確認する
4. コミットは**必ず両方を1コミットに含める**（片方だけのコミットを作らない）

### なぜ自動化しないか

Markdown → HTML の変換には parser が必要で、依存ゼロの原則（§2）に反する。
自前で書けば保守対象が増える。**年に数回しか変わらない文書のために構成を崩さない。**

### ずれの検出

リリース前チェック（§11）に「マニュアルの見出し数が両者で一致するか」を入れてある。
完全な検証ではないが、セクションの追加漏れは捕まえられる。

## 8. 警告と `helpId` の対応

`advisor.js` が返す警告オブジェクトは以下の形。

```js
{ level: 'info' | 'warn' | 'alert', message: string, helpId: string }
```

**`helpId` は必須。** 全ての警告がマニュアルのセクションを1つ持つ。
対応表は `docs/exposure-app-manual.md` §0.5 にある。

### 警告を追加するとき

1. 計算仕様 §9 の表に条件・レベル・文言を追加
2. `advisor.js` に実装。`helpId` を必ず付ける
3. マニュアル §0.5 の対応表に1行追加
4. 対応するセクションがマニュアル本文に無ければ**新設する**（既存セクションへの流用は可）
5. `index.html` にアンカーを追加
6. テスト #33（全警告が有効な `helpId` を持つ）が緑であることを確認

**5 を飛ばすと `?` を押しても何も起きない。** テスト #33 は ID の存在を検証するが、
`index.html` 側のアンカーの実在は検証していない（DOM を見ないため）。ここは目視。

## 9. localStorage スキーマとマイグレーション

### キー

| キー | 内容 |
| --- | --- |
| `expo:settings` | 機材設定・ストロボプロファイル・校正値・所有ND |
| `expo:lastState` | 直近の選択（シーン・意図・焦点距離・距離など） |

### 必ず守ること

```js
// storage.js
try {
  const raw = localStorage.getItem('expo:settings');
  const stored = raw ? JSON.parse(raw) : {};
  return { ...DEFAULTS, ...stored };   // ← 既定値とマージする
} catch {
  return DEFAULTS;                     // ← 失敗しても機能を落とさない
}
```

**必ず `try/catch` で包む。** プライベートブラウズでは `localStorage` へのアクセスが例外を投げる環境がある。
**必ず既定値とマージする。** 設定項目を追加したとき、既存ユーザーの保存データにその項目は無い。
マージしないと `undefined` が計算に流れ込んで `NaN` になる。

### スキーマを変えるとき

`expo:settings` に `schemaVersion` を持たせてある。

| 変更の種類 | 対応 |
| --- | --- |
| **項目の追加** | 何もしない。既定値マージで吸収される |
| **項目名の変更** | `schemaVersion` を上げ、読み込み時に旧名から移送する |
| **意味の変更**（単位・基準が変わる） | `schemaVersion` を上げ、**値を変換する。** 変換なしで放置すると静かに間違う |
| **項目の削除** | 何もしない（マージで無視される） |

**最も危険なのは「意味の変更」。** 例えば `hssBaseLoss` の定義を変えると、
ユーザーが調整した値が別の意味に解釈される。この場合は移送コードを書くか、
その項目だけ既定値に戻して通知する。

### 校正値の扱い

`k`（機材係数）はユーザーが**テスト撮影して得た実測値**であり、再取得にコストがかかる。

**`flash.js` の推定式 `GN = k√Ws` を変えてはいけない。**
式を変えると、保存済みの `k` の意味が変わり、ユーザーの校正が無音で無効になる。
バッジも「校正済み」のまま残るため、**間違った値を正しいと信じて使うことになる。**

どうしても変える必要がある場合は、`schemaVersion` を上げて全プロファイルを未校正に戻し、
「校正のやり直しが必要です」と明示すること。

## 10. 近似モデルの一覧

**このアプリには「厳密な計算」と「目安」が混在している。** どれがどちらかを把握していないと、
精度改善のつもりで実用性を壊す。

| モデル | 性格 | 精度 | 変更時の注意 |
| --- | --- | --- | --- |
| 露出方程式（EV / F / SS / ISO） | **厳密** | 誤差なし | 変える理由がない |
| 1/3段テーブル | **厳密**（ラベルは慣用表記） | — | インデックス体系は保存データに影響 |
| ND の減光段数 | **厳密**（公称値） | — | 可変NDは対象外（§12） |
| シーンEV | 目安 | ±1段 | 微調整UIがあるので過度に詰めない |
| `GN = k√Ws` | 目安 | 校正前は±1.5段 | **§9 の警告を読む** |
| モディファイア減光 | 目安 | 製品差大 | 校正で吸収される |
| HSS 基準損失 | 目安 | 機種差大（1.0〜2.5段） | ユーザー調整可。既定値を動かすと全員の計算が変わる |
| 閃光時間 | 目安 | 機種差大 | 判定に使うだけで結果値には影響しない |
| 手ブレ限界（1÷焦点距離） | 目安 | ±1段 | 1/3段未満の不足では警告しない設計 |

**目安の項目を「より正確な値」に差し替える提案には慎重になること。**
機種差のほうが大きいので、平均値を精密にしても現場では当たらない。
**校正機構とユーザー調整のほうが効く。** これが設計の方針。

## 12. 設計上の割り切り（変更提案が来たときの根拠）

| 決定 | 理由 | 見直す条件 |
| --- | --- | --- |
| ビルドステップなし | 数年後に `npm install` が通らなくなる。依存ゼロなら壊れない | 依存が必要な機能が主要要件になったとき |
| 外部リソースゼロ | 電波のない撮影現場で使う。1件の外部参照でオフラインが死ぬ | なし（要件そのもの） |
| フルサイズ固定 | 換算計算を入れると全UIにセンサー選択が波及する | 別センサーの機材を常用するようになったとき |
| 多灯非対応 | ライティング比の計算はUIが別物になる。プロファイル切替で代替 | 2灯同時運用が主になったとき |
| 可変ND 非対応 | 実効段数が目盛りと一致せず、推定するとかえって外れる | なし（原理的に困難） |
| ND経路とHSS経路を自動選択しない | どちらが良いかは撮影意図で変わる。機械が決められない | なし（設計の中核） |
| SW の自動リロードなし | 計算中に画面が飛ぶのが最悪 | なし |
| マニュアルを手で二重管理 | 自動化には parser が必要で依存ゼロに反する | マニュアルが月次で変わるようになったとき |
| Markdown 仕様書を repo 内に置く | オフラインで読める。AI 作業者が参照できる | なし |

## 13. ユーザー報告からの切り分け

| 症状 | 疑う順序 |
| --- | --- |
| 修正したのに反映されない | ① `sw.js` の `CACHE` 上げ忘れ ② ユーザーが更新バーを押していない |
| オフラインで白画面 | `sw.js` の `ASSETS` に追加漏れ。オンラインでは再現しない |
| 設定が毎回消える | プライベートブラウズ。またはサイトデータ削除 |
| 計算が実際と1段ズレる | シーンEVの微調整未設定。または露出補正の符号 |
| ストロボが計算より暗い | 未校正（§11 の校正へ誘導）。またはモディファイア設定漏れ |
| HSSだけ暗い | `hssBaseLoss` が機種と不一致。設定タブで調整 |
| 数値が `NaN` になる | 保存データに新項目が無い。既定値マージの漏れ（§9） |
| iOS で入力時に画面がズームする | 入力欄の `font-size` が 16px 未満 |
| 一部の値だけ1/3段ずれる | 計算途中で `snap()` している。表示直前の一度だけにする |
| `?` を押しても何も出ない | `index.html` のアンカー欠落（§8 の手順5漏れ） |
