**`advisor.js` と `compute.js` の境界：** 意図別ロジック（ぼかす／止める／風景／夜手持ち）と
警告の組み立ては **`compute.js`** にある（当初の想定から移した）。
`advisor.js` は「1条件→1警告」または「日中シンクロの2経路」の粒度に留める。

`[純]` = 副作用ゼロの純粋関数のみ。DOM・`localStorage`・`window` に触らない。
`[定]` = 定数のみ。ロジックを持たない。

**呼び出しの向き：** `ui.js` → `compute.js` → `advisor.js` → `exposure`/`flash`/`filters`/`stops`/`scenes`。
`flash.js` などの計算モジュールは **`compute.js` 経由で使われる**のが原則で、`ui.js` から直接呼ぶのは
`stops`（表示ラベル）と `flash.calibrate()`（校正）だけ。ここを崩すと計算が2箇所に散る。

### 触るときの影響範囲

| ファイル | 変えると影響する先 | 注意 |
| --- | --- | --- |
| `stops.js` | **全計算**（`compute.js` 経由で全画面） | インデックス体系を変えると保存済み `manual.fIndex` 等が無効になる |

| `compute.js` | **結果パネル・3タブの表示すべて** | `derived` の形を変えたら `ui.js` の描画と `tests.html` の統合テストが連動する。タブ分岐は入口の1箇所だけに置く |

| `sw.js` | **更新の配信そのもの** | §6 を必ず読む |
| `index.html` | 全部 + プリキャッシュ対象 | ファイルを追加したら `sw.js` のリストにも足す（§6） |

## 4. 絶対に変えてはいけないこと

`CLAUDE.md` に全文がある。ここでは**変更提案が来たときに却下する根拠**として要点だけ挙げる。

### 配布形態

- **外部リソース参照ゼロ。** 1行の CDN 参照でオフラインが死ぬ。これが最も起きやすい退行
- **すべて相対パス。** GitHub Pages のプロジェクトサイトは `/<repo>/` 配下。`/css/style.css` は 404
- `manifest.webmanifest` の `start_url` と `scope` は `"./"`
- `sw.js` はルート直下（スコープの都合）

### ドメインの物理

これらを壊すと**計算が静かに間違う**。テストが守っているので、赤くなったら実装ではなく理解を疑う。

| 不変条件 | 守るテスト |
| --- | --- |
| SS はストロボ露出に影響しない | #26 |
| ND はアンビエントとストロボの両方に等しく効く | #27 |
| 1/3段への丸めは表示直前の一度だけ | #1〜#9 全般 |
| 表示ラベルと厳密値は一致しない（`15″`の実体は16秒） | #30 |
| 距離は「ストロボ→被写体」であってカメラからではない | — |
| Ws から GN は一意に決まらない（校正前提） | #13, #14 |
| ND経路と HSS経路は両方計算して並べる（自動選択しない） | #21〜#23 |
| 発光量が大きいほど閃光時間は長い | #28, #29 |

### UI

- 通常操作でソフトキーボードを出さない
- 結果パネルはどのスクロール位置でも見えている
- 範囲外入力を拒否せずクランプして通知する
- 入力欄の `font-size` は 16px 以上（下回ると iOS が自動ズームする）
- **公称ラベル（F2.8 / 1/250）を厳密値として計算に使わない。** `compute()` の入口の
  `exactGear()` で 1/3段グリッドの厳密値（2.8284 / 1/256）へ直す。下記
- **タッチで操作する要素には `touch-action` を宣言し、`touchcancel`（Pointer Events では
  `pointercancel`）を必ず処理する。どちらか欠けるとスクロールとの競合で状態が壊れる。**
  キャンセルは**値を確定しない**。詳細は下記

### 公称ラベルを厳密値として使わない（実機で不具合が出た箇所）

**症状：** 快晴 EV15 / ISO200 / F2.8 / 同調 1/250 / 背景−1段 で、
**ND8+ND16（7段）が選ばれた。正しくは 6.0段 ちょうどで ND4+ND16（2枚）。**

**原因：** 設定は人が読める**公称値**で保存される（`lens.fMin = 2.8`、`camera.syncSpeed = 1/250`）。
これを厳密値として計算すると、本来ちょうど 6.0段 の壁が **6.06段** になる。
ND は整数段しかないので `Math.ceil` が**まるごと1段多い ND** を要求する。

| 公称 | 1/3段グリッドの厳密値 | ずれ |
| --- | --- | --- |
| F2.8 | 2.8284 | 0.029段 |
| F11 | 11.314 | 0.081段 |
| 1/250 | 1/256 | 0.034段 |
| 1/60 | 1/64 | 0.093段 |
| 1/8000 | 1/8192 | 0.034段 |

**`compute()` の入口で1度だけ `exactGear()` を通して厳密値へ直す。**
対象は `lens.fMin` / `lens.fMax` / `camera.syncSpeed` / `camera.maxSS`。
ISO は公称と厳密が一致する（200 = 50·2²）ので不要。焦点距離・距離・Ws は 1/3段の量ではない。

**個々の計算で snap し直さないこと。** 入口で正規化する形を崩すと、どの経路が厳密値で
どれが公称値かが追えなくなる。

#### `CEIL_EPS`（1e-9）と混同しないこと

`Math.ceil` の許容誤差 `advisor.CEIL_EPS` は **IEEE754 の丸め誤差だけ**を吸収する。

```
2 ** (i/6) で作った 1/3段の値どうしの比を log2 で段数に戻すと、
本来ちょうど 6.0 のところが 6.000000000000001 になることがある
  → 素の Math.ceil は 7 を返す（ND がまるごと1段増える）
```

**誤差は「比を `log2` で段数化する経路」全般で発生する。**
1/3段グリッドの全組み合わせ（40×40）を走査した結果：

| 経路 | 整数近傍の誤差が乗る組み合わせ |
| --- | --- |
| `2·log2(F/F)`（`daylightSync` の壁） | **215 / 1600** |
| `log2(N²/t)`（`solveSS` 由来） | **28 / 1600** |

**約13%。`CEIL_EPS` は特定の経路の保険ではなく、段数を切り上げるすべての箇所で必要。**

> **過去に「誤差が出るのは F値を2乗する経路だけ／比のまま扱う `daylightSync` は誤差が出ない」と
> 書いていたが誤り。** 検証した1件（F2.8 と 1/250）ではたまたま比が正確に 8.0 になっただけで、
> 一般には成り立たない。走査で 215/1600 が反証。

**公称値の 0.03〜0.09段 は桁が7つ違うので、この誤差では吸収できない。**
`CEIL_EPS` を大きくして誤魔化すと、**本当に切り上げが要る 6.1段 を 6段 と答えるようになる。**
原因の側（公称値）で直す。

**走査の再現方法**（ツール化はしていない。N2a・N2b で境界が固定できていれば足りる）

```js
// F(i) = 2 ** (i/6) として全 i,j について
const v = 2 * Math.log2(F.real(i) / F.real(j));
// |v − round(v)| が 0 より大きく 1e-9 未満のものを数える
```

テストは3件で守る。

| # | 種類 | 何を守るか |
| --- | --- | --- |
| **N1** | 統合 | 公称値（F2.8 / 1/250）で入力しても壁が 6.0段 になる（`exactGear` の配線） |
| **N2a** | 単体 | `6.000000000000001` を**リテラルで**渡し、素の `ceil` は 7・`CEIL_EPS` 付きは 6 |
| **N2b** | 統合 | 実際の経路（F1.8 希望・同調で F14 適正）で 6段 が選ばれる（`CEIL_EPS` の配線） |

**N2a はリテラルで渡すこと。** パイプラインを通して誤差を作ろうとすると、
途中の演算で吸収されて空振りする（一度これで失敗した）。

### タッチのジェスチャ境界（実機で不具合が出た箇所）

**症状：** ホイールを横スワイプ中に縦スクロールが挟まるとダイヤルが大きく飛び、繰り返すと悪化。
PC では再現しない（マウスではスクロールと競合しないため）。

**原因は2つが重なっていた。**

| 欠けていたもの | 何が起きたか |
| --- | --- |
| `touch-action` の宣言（操作要素） | 縦スクロールが始まると**ブラウザがタッチを引き取り** `pointercancel` が飛ぶ |
| キャンセルの正しい処理 | `pointercancel` が**確定処理に繋がっていた**ため、ユーザーが選んでいない値が commit された。飛んだ値が次のジェスチャの起点になるので**悪化した** |

**守ること。**

1. **`touch-action` は操作要素だけに付ける。** 親のスクロールコンテナには付けない
   （ページ全体のスクロールが壊れる）。横操作なら `pan-y`、**`none` にしない**
   （その要素の上から始めた縦スクロールができなくなる）
2. **キャンセルで値を確定しない。** ドラッグ状態を捨てて開始時の位置へ戻す。
   システム都合（電話着信・通知・システムジェスチャ・ブラウザUI）の中断で、
   ユーザーが選んでいない値を残してはいけない
3. **ジェスチャの状態は1つのオブジェクトに閉じる**（`js/wheel.js` の `drag`）。
   個別の変数に散らすと、どれか1つを消し忘れて前のジェスチャが次に持ち越される
4. **開始時に状態を作り直す。** `startIndex` は現在値から取り直し、`pointerId` を保持して
   同じ指のイベントだけを追う。ドラッグ中に新しい `pointerdown` が来たら前を破棄して始める
5. **位置の計算は純粋関数に切り出す**（`wheel.indexFromDrag`）。引数が
   「開始位置・総移動量・step・長さ」の4つだけなら、**累積の誤りが構造的に起こり得ない。**
   テスト D1〜D3 がこれを守る

**採らない案：** 「1秒以上停止したらスクロールを許可する」。遅延が体感を悪くし、判定の条件が
増えて別の不具合を生む。`touch-action` は宣言1行でブラウザ側が処理する（UI仕様 §3 に記録）。

## 5. 開発環境と動かし方

```bash
cd ~/projects/Exp_assist

python3 -m http.server 8000

# アプリ
```

| 段階 | 方法 | 制約 |
| --- | --- | --- |

  （バックアップ：`/etc/apt/sources.list.bak`）。新規パッケージ導入時も同様
- プロジェクトは `/home/` 配下に置く。`/mnt/c/` はファイルI/Oが遅く、Service Worker の検証で待たされる

## 6. Service Worker の更新手順（最重要）

**ここを間違えると、修正がユーザーに永久に届かない。** 最も事故が起きやすい箇所。

### 6.1 何かファイルを変えたら

```js
// sw.js 冒頭
const CACHE = 'expo-v3';   // ← 必ずインクリメントする（現在の値）
```

**バージョンを上げ忘れると、ユーザーの端末は古いキャッシュを返し続ける。**
オフライン優先のキャッシュ戦略なので、ネットワークを見に行かない。修正が届かない。

#### 何回上げるか — 1回のデプロイにつき1回

バージョンを上げる目的は、**配信済みの版を置き換えること**である。
したがって**1回のデプロイにつき1回上げれば足りる。**
既に上げたがまだ push していない場合、追加の変更で**再度上げる必要はない。**

**判断の基準は「リリース済みの `CACHE` 値と異なるか」であり、「前回の編集から変わったか」ではない。**

| 状況 | 上げる？ |
| --- | --- |
| リリース済み v2 → 未 push の v3 に、さらに変更を足す | **上げない。** v3 のままで v2 の利用者全員に届く |
| リリース済み v3 → 変更を足す | 上げる（v4） |
| 未リリースの v3 をローカルで何度も直す | 上げない |

v3 が一度もデプロイされていなければ、v3 をキャッシュしている利用者は存在しない。
不要に上げると、追跡すべき版が増えるだけで誰にも届き方が変わらない。

> **ローカルで検証中に古いキャッシュを掴む場合**は、DevTools の **Update on reload** か
> §6.6 の手動削除で対処する。**それは `CACHE` を上げる理由にはならない。**

### 6.2 ファイルを追加したら

**`ASSETS` に足す。追加を忘れると、オンラインでは動くがオフラインで壊れる。**
開発中は常にオンラインなので**気づかない**。これが2番目に多い事故。

```bash
bash tools/check-sw-assets   # 追加漏れを機械的に検出する（リリース前チェックに含める）
```

このツールは2方向を見る。

| 検査 | 意味 |
| --- | --- |
| `MISSING(assets)` | 参照されているのに `ASSETS` に無い → **オフラインで壊れる** |
| `MISSING(disk)` | `ASSETS` にあるのにディスクに無い → `addAll` が失敗し **SW が入らない** |

**現在の ASSETS（20件）**

```
'./'                        './index.html'              './manifest.webmanifest'
'./css/style.css'
'./js/main.js'              './js/compute.js'           './js/state.js'
'./js/ui.js'                './js/wheel.js'             './js/storage.js'
'./js/stops.js'             './js/exposure.js'          './js/flash.js'
'./js/filters.js'           './js/advisor.js'           './js/scenes.js'
'./icons/icon-192.png'      './icons/icon-512.png'
'./icons/icon-maskable.png' './icons/apple-touch-icon.png'
```

**意図的に入れないもの（将来「なぜ無いのか」を追えるように残す）**

| 除外 | 理由 |
| --- | --- |
| `tools/` | 開発用スクリプト。アプリの実行に不要 |
| `docs/` | 仕様書・マニュアル原稿。アプリが読むのは `index.html` 内の写しだけ |
| `tests.html` | 開発用の検証ページ。オフラインで動かす必要がない |
| `sw.js` 自身 | ブラウザが管理する。キャッシュ対象にしない |

**テスト #33 は `docs/exposure-app-manual.md` を fetch する。** そのため
**SW 登録後にオフラインで `tests.html` を開くと #33 が失敗する。これは想定どおりの挙動。**
テストはオンライン（ローカルサーバー）で実行する。

### 6.3 install は HTTP キャッシュをバイパスする

```js
// sw.js の install
await cache.addAll(ASSETS.map((u) => new Request(u, { cache: 'reload' })));
```

**`cache: 'reload'` を外すと、`CACHE` を上げても古い中身を掴む。** 3番目の事故。

変更したファイルがブラウザの **HTTP キャッシュ**に残っている間に `install` が走ると、
そこから返された古い版をプリキャッシュしてしまう。GitHub Pages は `max-age=600` を返すので、
**push 後10分間はこのリスクがある。** バージョンを上げたのに中身が古いという、最も検出しにくい形になる。

**確認方法：** DevTools → Application → Cache Storage → `expo-vN` の
**`Time Cached` が全件で同一かを見る。** 一部だけ古い時刻なら HTTP キャッシュ経由で入っている。

### 6.4 リリース時の必須手順

1. `sw.js` の `CACHE` を上げた
2. `ASSETS` に新規ファイルを追加した
3. push 後、**機内モードで全機能を確認**した
4. DevTools → Application → Service Workers で古い SW が削除されているか確認した

### 6.5 更新の見え方（設計として意図している）

- 新しい SW は `waiting` に入るだけで、**自動でアクティブにならない**
- ヘッダーに「新しいバージョンがあります ［更新］」バーを出す
- **押されたときだけ** `skipWaiting()` → `reload()`

**自動リロードを実装しないこと。** 現場で計算中に画面が飛ぶのが最悪の体験。
「すぐ反映されないのは不便だ」という理由で自動化する提案は却下する。

### 6.6 キャッシュを手で消したいとき

```js
// DevTools のコンソールで
caches.keys().then(ks => ks.forEach(k => caches.delete(k)));
navigator.serviceWorker.getRegistrations().then(rs => rs.forEach(r => r.unregister()));
```

その後リロード。開発中に古いコードを掴んで離さないときに使う。

### 6.7 「オフラインで使えるようになりました」通知

`js/main.js` には SW 関連の配線が**2本ある。混ぜないこと。**

| 配線 | 契機 | 出るもの |
| --- | --- | --- |
| `showUpdateBarIf` | `waiting` が現れた（＝更新がある） | 更新バー（§6.5） |
| `watchFirstInstall` | `controller` が居ない状態で `activated` になった | トースト（一度きり） |

**なぜ要るか（実機で確認された挙動）。** iOS ではホーム画面に追加しただけではキャッシュができない。

```
ホーム画面に追加 → すぐ機内モードで起動 → 失敗
一度オンラインで起動 → 機内モードで起動 → 成功
```

ホーム画面のアプリは自前の保存領域を持つため、そこにプリキャッシュが載るまで一度の
オンライン起動が要る。**iOS の仕様でありコードの不具合ではないが、利用者には見えない。**
現場に着いてから追加しても間に合わない、という事故になるので画面に出す。

`controller` が居ない＝まだ SW に制御されていない＝この起動が初回インストール。
その worker が `activated` に入った時点で `install` の `waitUntil`（`addAll`）は完了している。

フラグは `localStorage` の **`expo-flags-v1`**（アプリ状態の `expo-state-v1` とは別キー）。
分けている理由は2つ：`compute` の入力ではないので `schemaVersion` を上げたくないことと、
設定をリセットしたときに初回通知が再び出ないようにするため。

トーストの DOM は `ui.js` が持つ。`main.js` は `showToast()` だけを使い、
**自前でトースト要素を作らない**（二重管理になる）。

## 7. マニュアル本文の二重管理

マニュアルは**2箇所に存在する。**

| 場所 | 役割 |
| --- | --- |
| `docs/exposure-app-manual.md` | **正典。** 原稿・レビュー対象 |
| `index.html` 内の `<div id="manual">` | 写し。実際にユーザーが読むもの |

ビルドステップがないため自動同期できない。**運用ルールで担保する。**

### 変更手順

1. `docs/exposure-app-manual.md` を直す
2. `index.html` の該当セクションに反映する
3. `<a id="help-xxxx">` のアンカーが消えていないか確認する
4. コミットは**必ず両方を1コミットに含める**（片方だけのコミットを作らない）

### なぜ自動化しないか

Markdown → HTML の変換には parser が必要で、依存ゼロの原則（§2）に反する。
自前で書けば保守対象が増える。**年に数回しか変わらない文書のために構成を崩さない。**

### ずれの検出

```bash
bash tools/check-help-anchors
```

**markdown 本文（§1 以降）の全アンカー ID が `index.html` に実在するか**を突き合わせる。
警告から参照されないセクション（目次からのみ辿るもの）も対象に含む。

**見出し数の一致では検出できない。** 1つ増えて1つ減れば数は合ってしまうため、
数ではなく ID の集合で比べる。加えて、数え方そのものを間違えやすい
（§0 の組み込み仕様は本文ではないので数に入れてはいけない）。

このツールが見るのは2つ：

| 検査 | 対象 |
| --- | --- |
| `MISSING(helpId)` | §0.5 の対応表にある `helpId` が `index.html` に無い |
| `MISSING(section)` | 本文のアンカー ID が `index.html` に写されていない |

**本文の文章そのものが一致しているかは検証できない。** 見出しとアンカーの存在までが機械の担当で、
文言の同期は §7 の運用ルール（markdown を先に直す）で担保する。

## 8. 警告と `helpId` の対応

`advisor.js` / `compute.js` が返す警告オブジェクトは以下の形。

```js
{ level: 'info' | 'warn' | 'alert', icon: string, helpId: string, message: string }
```

**`helpId` は必須。** 全ての警告がマニュアルのセクションを1つ持つ（「この設定で撮れます」も含む）。
**ID 文字列の定義場所は `js/scenes.js` の `HELP` だけ。** 実装に直書きしない。
対応表は `docs/exposure-app-manual.md` §0.5 にあり、**実装が正典**（表を実装に合わせる）。

### 警告を追加するとき

1. 計算仕様 §9 の表に条件・レベル・文言を追加
2. `js/scenes.js` の `HELP` に値を追加（既存セクションへの流用は可）
3. `advisor.js` / `compute.js` に実装。`helpId: HELP.xxx` を必ず付ける
4. マニュアル §0.5 の対応表に1行追加
5. 対応するセクションがマニュアル本文に無ければ**新設する**
6. `index.html` にアンカー `<a id="help-xxxx"></a>` を追加
7. 下の2つを実行して両方通ることを確認

```bash
bash tools/check-help-anchors   # 対応表の helpId が index.html に実在するか
# tests.html を開いて #33 が緑（全警告が表内の helpId を持ち、HELP の全値が発生する）
```

**6 を飛ばすと `?` を押しても何も起きない。** テスト #33 は helpId が対応表にあることまでしか
検証できない（DOM を見ないため）。`index.html` 側のアンカー実在は
**`tools/check-help-anchors` が機械的に検査する**（欠落を一覧して終了コード 1）。目視に頼らない。

> マニュアル本文をまだ `index.html` に写していない段階では、このツールは全件欠落で落ちる。
> それが正しい状態で、写しの完了判定に使う。

### 8.1 警告に解決ボタンを付ける（`action`）

設定を直せば解決する警告には、警告の中に直せるボタンを置く。設定タブへ移動させない。

```js
{ level, icon, helpId, message, action: { kind: 'raiseCeiling', to: 1, label: '上限を 1/2 に上げる' } }
```

`compute()` は **`action` を純粋なデータとして組み立てるだけ**で、DOM も `setState` も知らない。
`ui.js` の `warnHtml` が `data-action` / `data-to` 付きのボタンを描き、`el.warnings` の
イベント委譲が受ける。**新しい再描画経路を作らないこと**（`setState` の一本だけ）。

**文言に出す値とボタンが設定する値は同じ変数から作る。** `action.label` を組み立てるのも
`data-to` に入れるのも `action.to` ひとつ。別々に計算すると片方だけ直したときに食い違う。

`raiseCeiling` では**上限（`to`）と、その上限で実際に使われる発光量（`resultPowerStops`）が
1段ずれることがある**（上限は `floor(over)`・発光量は `round(over)`）。
実機で「1/1 に上げると出たのに 1/2 になった」という報告が出たため、文言に両方を出している。
`resultPowerStops` の式は `resolvePowerWithCeiling` と同一にすること。
ずれたら表示だけが嘘になる。テスト **W7** がこの3つ（文言・`action`・適用後の結果）の一致を見る。

### 8.2 提案が別の警告を生まないことを検証する（最重要の不変条件）

**「その提案を適用したら別の警告に置き換わる」ものを提示してはいけない。**
実機で次の袋小路が起きた。

```
背景が明るすぎる → ND を足す → ストロボが上限を超える
  → 「ND を1枚外す」と提案される → 背景が明るすぎる（元に戻る）
```

原因は ND がアンビエントとストロボの**両方に等しく効く**こと。片側の不足を ND で直すと
もう片側が崩れる。アプリ自身の提案がユーザーを元の問題へ戻していた。

**検証の方法（循環依存を避けた設計）**

提案を当てた状態で `compute()` を再実行して警告を数える方法は**採らない。**

- `advisor` から `compute` を呼ぶと循環依存になる（`compute` が `advisor` を呼んでいる）
- 提案の数だけ全体計算が走る

代わりに**解析的に判定する。** 各計算経路が「その軸に何段の余地があるか」を1つの数値として出し、
`compute.ndRemovalOption()` がそれと比べるだけ。

| 経路 | `d.ndRemovable.slack`（アンビエントが明るくなれる余地） |
| --- | --- |
| `computeManual`（計算タブ） | 自由軸が明るい側の限界まで動ける段数（`LIMITS` の `loKind`/`hiKind` から引く） |
| `computeSlow` | `log2(SS / maxSS)`（SS が速くなれる段数） |
| `computeDaylight` | `ndPath.totalStops − wallStops`（同調速度の壁に要る量を超えた余剰） |

**`d.ndRemovable` は `resolveFlashSide()` を呼ぶ前に必ず立てる。** 立て忘れると
フォールバック（`slack: 0`）で ND を外す提案が一切出なくなり、静かに劣化する。

新しい提案を足すときは、その提案が動かす軸の余地を同じ形で用意すること。

## 9. localStorage スキーマとマイグレーション

### キー

| キー | 内容 | 定義場所 |
| --- | --- | --- |
| `expo-state-v1` | **アプリ状態のすべて。** 機材設定・プロファイル・校正値・所有ND・直近の選択（シーン・意図・焦点距離・距離）・UI状態（タブ・テーマ・パネル高さ） | `js/storage.js` の `KEY` |
| `expo-flags-v1` | 一度きりの通知フラグ（`offlineReadyNotified`）。**アプリ状態ではない** | `js/storage.js` の `FLAG_KEY` |

**設計と実装が食い違っていた点（手順11で修正）：** 当初の設計は
`expo:settings` と `expo:lastState` の2キーに分ける想定だったが、実装は**単一 state を
1キーに丸ごと保存**している。`setState` の直後に1箇所で保存する方針（CLAUDE.md）と
噛み合うのはこちらで、分割すると保存経路が2つになる。上の表が現在の正典。

**フラグを state に混ぜないこと。** `compute()` の入力でも描画の材料でもないので、
混ぜると `schemaVersion` を上げる必要が出るうえ、設定リセットで初回通知が再び出る（§6.7）。

**キー名にバージョンを含めている。** 破壊的変更時は `migrate()` で移送するのが原則で
（`schemaVersion` を上げる）、キー名の `v1` を上げるのは**移送を諦めて捨てるとき**だけ。

#### 単一キーのトレードオフ（記録・現状維持）

**現在は単一キー。シーンを変えるだけの書き込みでも、校正値を含む全体が書き直される。**

起動時の保存抑止（`ui.init` が `setState({}, { persist: false })` で初回描画する）により
**最悪のケース——読み込み失敗で既定値へフォールバックした直後に上書きし、校正値を
復旧不能にする——は防いでいる。**

それでも、**設定（実測で得た貴重な値：`profiles[].cal` の k）と一時状態（使い捨て：シーン・
意図・パネル高さ）を分離すれば、リスクそのものを切り離せる。** 一時状態の書き込みが
何回失敗しても校正値には触れない、という形にできる。

**現状維持とする理由：** 分離には保存データの移行が必要で、現在の保護で実害が出ていない。
**書き込みの失敗が観測されたら分離を検討する**（`ui.warnStorageOnce` のトーストが出たという
報告が来たら、まずこの節を読むこと）。

### 必ず守ること

```js
// storage.js
try {
  const raw = localStorage.getItem('expo:settings');
  const stored = raw ? JSON.parse(raw) : {};
  return { ...DEFAULTS, ...stored };   // ← 既定値とマージする
} catch {
  return DEFAULTS;                     // ← 失敗しても機能を落とさない
}
```

**必ず `try/catch` で包む。** プライベートブラウズでは `localStorage` へのアクセスが例外を投げる環境がある。
**必ず既定値とマージする。** 設定項目を追加したとき、既存ユーザーの保存データにその項目は無い。
マージしないと `undefined` が計算に流れ込んで `NaN` になる。

### スキーマを変えるとき

保存データに `schemaVersion` を持たせてある（現行 **2**）。移行は `js/state.js` の
`migrate(loaded)`（純粋関数）で行い、`ui.init()` が読み込み直後に一度だけ呼ぶ。
純粋関数なので `tests.html` #45 で検証できる。

**v1 → v2 の移行内容**

| 変更 | 種類 | 移行 |
| --- | --- | --- |
| `profile.calibrated`(boolean) → `profile.cal`(オブジェクト) | 意味の変更 | `calibrated: true` の `k` を `cal.reflector` へ移送（標準リフレクターは既定なので校正時に選ばれていた可能性が最も高い）。`calibrated` は削除 |
| MODIFIERS のキー削除（アンブレラ／ソフトボックス／ビューティディッシュ／ベアバルブ） | 項目の削除 | 保存済みの `modifier` が未知のキーなら **標準リフレクターへフォールバック**（放置すると減光段数が `undefined` → `NaN` になる） |
| `powerCeilingStops` の追加 | 項目の追加 | 既定値マージ（無ければ 2 を入れる） |

移行が走ったときは**一度だけトースト**で通知する：
「モディファイアごとの校正に対応しました。標準リフレクター以外は再校正が必要です」

**校正値 k は破棄せず必ず移送する**（実測しないと得られないため）。

| 変更の種類 | 対応 |
| --- | --- |
| **項目の追加** | 何もしない。既定値マージで吸収される（例：`ui.panelSize` の追加は `schemaVersion` を上げていない） |
| **項目名の変更** | `schemaVersion` を上げ、読み込み時に旧名から移送する |
| **意味の変更**（単位・基準が変わる） | `schemaVersion` を上げ、**値を変換する。** 変換なしで放置すると静かに間違う |
| **項目の削除** | 何もしない（マージで無視される） |

**最も危険なのは「意味の変更」。** 例えば `hssBaseLoss` の定義を変えると、
ユーザーが調整した値が別の意味に解釈される。この場合は移送コードを書くか、
その項目だけ既定値に戻して通知する。

### 校正値の扱い

`k`（機材係数）はユーザーが**テスト撮影して得た実測値**であり、再取得にコストがかかる。

**`flash.js` の推定式 `GN = k√Ws` を変えてはいけない。**
式を変えると、保存済みの `k` の意味が変わり、ユーザーの校正が無音で無効になる。
バッジも「校正済み」のまま残るため、**間違った値を正しいと信じて使うことになる。**

どうしても変える必要がある場合は、`schemaVersion` を上げて全プロファイルを未校正に戻し、
「校正のやり直しが必要です」と明示すること。

## 10. 近似モデルの一覧

**このアプリには「厳密な計算」と「目安」が混在している。** どれがどちらかを把握していないと、
精度改善のつもりで実用性を壊す。

| モデル | 性格 | 精度 | 変更時の注意 |
| --- | --- | --- | --- |
| 露出方程式（EV / F / SS / ISO） | **厳密** | 誤差なし | 変える理由がない |
| 1/3段テーブル | **厳密**（ラベルは慣用表記） | — | インデックス体系は保存データに影響 |
| ND の減光段数 | **厳密**（公称値） | — | 可変NDは対象外（§12） |
| シーンEV | 目安 | ±1段 | 微調整UIがあるので過度に詰めない |
| `GN = k√Ws` | 目安 | 校正前は±1.5段 | **§9 の警告を読む** |
| モディファイア減光 | 目安 | 製品差大 | 校正で吸収される。**オクタは径で段数が変わる**（30cm:1.5 / 60cm:2.0 / 90cm:2.5段）。面積が大きいほど拡散して減光が増える関係。校正値は**プロファイル×モディファイアごと**に保存され、未校正の組み合わせでは推定 `k` に戻る |
| ブラックミスト減光 | 目安 | 公称ほぼ0段 | 既定 0段（設定で 0〜0.33段）。ND とは別概念で `solveND` の探索対象外。ただし**枚数には数える**（ケラレのリスクは ND と同じ） |
| HSS 基準損失 | 目安 | 機種差大（1.0〜2.5段） | ユーザー調整可。既定値を動かすと全員の計算が変わる |
| 閃光時間 | 目安 | 機種差大 | 判定に使うだけで結果値には影響しない |
| 手ブレ限界（1÷焦点距離） | 目安 | ±1段 | 1/3段未満の不足では警告しない設計 |
| シーン別コントラスト目安 | 目安 | **±1段** | 「空が被写体より何段明るいか」。逆光は EV で区別できないので `flash.backlit` トグルで +2.0段。薄暮・屋内・夜間は `null`（判定しない）——最も明るい背景が光源そのもので、画角の切り方で決まるため表では当てられない |
| ハイライトヘッドルーム | 目安 | **機種差あり・調整可** | 既定 3.0（JPEG 相当）／RAW は 3.5〜4.0。設定タブで 2.0〜4.5。段数そのものより「選ぶべき背景段数」を出すことで誤差に耐える設計（仕様 §9.1） |

**目安の項目を「より正確な値」に差し替える提案には慎重になること。**
機種差のほうが大きいので、平均値を精密にしても現場では当たらない。
**校正機構とユーザー調整のほうが効く。** これが設計の方針。

## 11. リリース前チェック

## 12. 設計上の割り切り（変更提案が来たときの根拠）

| 決定 | 理由 | 見直す条件 |
| --- | --- | --- |
| ビルドステップなし | 数年後に `npm install` が通らなくなる。依存ゼロなら壊れない | 依存が必要な機能が主要要件になったとき |
| 外部リソースゼロ | 電波のない撮影現場で使う。1件の外部参照でオフラインが死ぬ | なし（要件そのもの） |
| フルサイズ固定 | 換算計算を入れると全UIにセンサー選択が波及する | 別センサーの機材を常用するようになったとき |
| 多灯非対応 | ライティング比の計算はUIが別物になる。プロファイル切替で代替 | 2灯同時運用が主になったとき |
| 可変ND 非対応 | 実効段数が目盛りと一致せず、推定するとかえって外れる | なし（原理的に困難） |
| ND経路とHSS経路を自動選択しない | どちらが良いかは撮影意図で変わる。機械が決められない | なし（設計の中核） |
| SW の自動リロードなし | 計算中に画面が飛ぶのが最悪 | なし |
| マニュアルを手で二重管理 | 自動化には parser が必要で依存ゼロに反する | マニュアルが月次で変わるようになったとき |
| Markdown 仕様書を repo 内に置く | オフラインで読める。AI 作業者が参照できる | なし |
| レンズはプロファイル化していない | 設定タブが長くなる。当面は単一レンズ設定で運用 | 複数レンズを使い分けるようになったとき（等価露出一覧の「開放より明るい行の使用不可表示」も自然に解決する） |
| 等価露出一覧を3行固定（2段刻み） | 6行だと結果パネル内でスクロールが要る。3択なら一覧性が保てる | 画面が大きい端末を主に使うようになったとき |
| 等価露出一覧の回折アイコン | 現3値（F2.8/F5.6/F11）では到達しないが、一覧値が可変になったときに必要 | 一覧値を設定化するか、レンズ登録を入れたとき |

### 12.0 結果パネルの3段階遷移は `max-height` をアニメーションする（意図的な例外）

```css
.result-panel { transition: max-height var(--dur-panel) var(--ease); }
```

**レイアウトを動かすため UI仕様 §16 の規則からは逸脱する。**
不変条件の目的はジャンク（コマ落ち）の防止で、本来の対象は**連続的・スクロール駆動**の
アニメーションである。ここは**離散操作（スワイプ／タップ）による 200ms の一度きりの遷移**で、
**実機（iPhone 16 Pro Max）で滞りがないことを確認した上での意図的な例外。**

**代替案（他の端末でジャンクが出たときはこちらへ切り替える）：**
パネルを常に `expanded` の高さで描画し、`translateY` で見える量を変える方式なら
コンポジタのみで完結する。中身の再レイアウトも起きない。

**この例外を増やさないこと。** レイアウトを動かすプロパティを新たにアニメーションさせるときは、
実機で確認したうえでこの節に1行足す。記録の無い例外は次の担当者が「規則違反」として直してしまう。

### 12.1 計算仕様 §9 にあるが実装しない警告（手順11で確定）

| 仕様 §9 の警告 | 実装しない理由 | 見直す条件 |
| --- | --- | --- |
| ND 装着でストロボ到達距離が半減以上（warn） | 結果パネルが「到達◯m（設定◯m）」を**常に**出しており、ND を付けた瞬間に数値が動く。同じ事実を警告で二重に言うと、日中シンクロでは ND がほぼ常用なので警告欄が恒常的に埋まり、本当に対処が要る alert が埋もれる | 到達距離の常時表示をやめたとき |
| HSS 損失 > 4段（warn） | 経路比較表が ND／HSS の**到達距離と損失段数を並べて**出す。段数を読んで選ぶ設計なので、片方に閾値警告を足すと「4.0段は良くて4.1段は悖い」という無い境界を作る | 経路比較表を畳んで既定で隠すようにしたとき |
| SS > 同調速度 かつ HSS 非対応／HSS off（alert） | `computeDaylight` の「同調速度の壁を越えられません。F を絞ってください」が同じ状態を1件で伝える（`prof.hss === false` なら `hssPath` が組まれず、ND でも足りなければこれが出る）。機種差（HSS 非対応）と設定差（HSS off）で文言を分けても対処は同じ | HSS の ON/OFF を撮影タブに出すようになったとき（いまはプロファイル設定のみ） |
| 必要 F < 開放F値（alert・かんたんタブ側） | 意図別ロジックは開放F値を**下限として使う**ので、かんたんタブでは必要 F が開放を下回る経路が無い（過剰分は SS 側に出て `overBrightWarning` が拾う）。計算タブでは `manualShort` が「F が◯段 足りません」を出す | F を自由に指定できる意図を追加したとき |

**3件とも「情報が無い」のではなく「同じ情報が別の形で常時出ている」。**
警告を足すと欄が埋まり、`alert` の識別性が落ちる。増やす前に結果パネルの表示を減らすこと。

### 12.2 その他の意図的な未実装（手順11で確定）

| 項目 | 状態 | 理由 |
| --- | --- | --- |
| モディファイアのグリッド／ディフューザー加算（`scenes.MODIFIER_ADDONS`） | 定数だけあり UI が無い | 校正がモディファイア単位で効くので、グリッド付きは「別のモディファイア」として校正するほうが正確。加算の推定値を足すと校正値と競合する。**定数は仕様 §7.5 の記録として残す** |
| UI仕様 §12「シーンを選ぶと計算を始めます」 | 未実装 | `state.scene` に既定値（快晴・順光）があり未選択状態が存在しない。初回セットアップでも必ず選ばせる |
| UI仕様 §12「この組み合わせは計算できません」 | 未実装 | `compute()` は全経路でクランプして必ず値を返す設計（入力を拒否しない原則）。想定外の例外に備えた包括 try/catch は、失敗を隠して原因追跡を難しくするので置かない |
| UI仕様 §12「所有している ND では最大10段までです」 | 文言を変えて実装 | 実装は「所有 ND（合計◯段）では ◯段 に届きません」。**必要段数と所有合計の両方**を出すほうが次の一手が決まる（仕様の文言は所有合計しか出さない） |
| `flash.requiredAperture` | 呼ばれない | 仕様 §5.3 の式。`reachDistance` と対で残す（詳細は関数の JSDoc） |
| `advisor.daylightSync` の `fAtSync` | js/ からは読まれない | テスト #19 が読む。同調速度で適正になるF値をラベル水準で検証する唯一の出口 |
| `ui.equivHtml` の空リスト分岐 | 到達しない | 等価露出一覧は常に3行返す。一覧を可変にしたら即必要（UI仕様 §12 の文言） |
| `advisor.isoFloorWarning` | アプリから呼ばれない | 意図別ロジックは ISO を下限から上げる方向にしか動かさない。将来 ISO 優先の意図で使う（`tests.html` #5b 直前のコメントに詳細） |

## 13. ユーザー報告からの切り分け

| 症状 | 疑う順序 |
| --- | --- |
| 修正したのに反映されない | ① `sw.js` の `CACHE` 上げ忘れ ② ユーザーが更新バーを押していない |
| オフラインで白画面 | `sw.js` の `ASSETS` に追加漏れ。オンラインでは再現しない |
| 設定が毎回消える | プライベートブラウズ。またはサイトデータ削除 |
| 計算が実際と1段ズレる | シーンEVの微調整未設定。または露出補正の符号 |
| ストロボが計算より暗い | 未校正（§11 の校正へ誘導）。またはモディファイア設定漏れ |
| HSSだけ暗い | `hssBaseLoss` が機種と不一致。設定タブで調整 |
| 数値が `NaN` になる | 保存データに新項目が無い。既定値マージの漏れ（§9） |
| iOS で入力時に画面がズームする | 入力欄の `font-size` が 16px 未満 |
| 一部の値だけ1/3段ずれる | 計算途中で `snap()` している。表示直前の一度だけにする |
| `?` を押しても何も出ない | `index.html` のアンカー欠落（§8 の手順5漏れ） |
