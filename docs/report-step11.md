## 2. 違反・未実装の詳細と判断

### A. `--flash` をアクセント色として広く使っている（違反・**未修正**）

CLAUDE.md の「絶対に破ってはいけない制約」と §16 の項目。`--flash` は
**ストロボ系統の識別にのみ**使う約束だが、実際には**アプリのアクセント色**として機能している。

| 用途 | 行 | ストロボ関連か |
| --- | --- | --- |
| フォーカスリング | `:85` | ✗ |
| タブの下線 | `:95` | ✗ |
| タイル選択 | `:166` | ✗ |
| チップ選択 | `:179,180` | ✗ |
| スライダーつまみ | `:194,196` | ✗ |
| トグル ON | `:219` | ✗ |
| ホイールのポインタ | `:273` | ✗ |
| トラックのロック | `:282` | ✗ |
| EV ルーラーの針・クリップ | `:356,357` | ✗ |
| 主ボタン | `:419` | ✗ |
| セットアップのドット | `:445` | ✗ |
| 目次トレイ開 | `:475` | ✗ |
| ストロボパネル枠・見出し | `:240,242,244,245` | ✓ |
| トラック名／値（`.is-flash`） | `:285,287` | ✓ |
| 同調速度の壁の数値 | `:340` | ✓ |
| ストロボの系統カード | `:363,365,368` | ✓ |

**判断：修正するが、この報告では実施しない。**

理由：`--accent` トークンを新設して16箇所を差し替える作業自体は機械的だが、
`--flash` と同値にするか別の色にするかで**見た目が変わるかどうかが決まる**。
同値なら見た目は不変（項目12のコントラスト実測をやり直す必要が無い）、別色なら再実測が必要。
**この選択はユーザーの設計判断**なので、確認のうえ次工程で行う。
放置ではなく「次にやる1件目」として §5 に載せる。

### B. `transform` / `opacity` 以外のアニメーション（違反・**未修正**）

| 対象 | 行 | 性質 |
| --- | --- | --- |
| `background` の遷移（タブ・タイル・チップ・グリップ・パネルハンドル） | `:116,162,176,217,322` | 押下フィードバック |
| `border-color` の遷移（タイル・チップ） | `:162,176` | 選択状態の変化 |
| `max-height` の遷移（結果パネルの3段階） | `:296` | **レイアウトを動かす** |

**仕様の中に矛盾がある（記録として残す）。**
UI仕様 §7 は「押下フィードバックは 80〜150ms 以内に返す（**背景色**または不透明度）」と
背景色を**明示的に許している**が、§16 と CLAUDE.md は「`transform`/`opacity` 以外を
アニメーションさせない」と禁じている。同じ文書の中で `background` の扱いが割れている。

**判断：**

- `background` / `border-color`（7箇所）は **§7 を採って現状維持**。押下フィードバックの
  ためのもので、コンポジタ外だが色の補間はレイアウトを起こさない。**§7 と §16 の矛盾を
  MAINTENANCE.md に記録する**（未記録のまま放置しない）
- `max-height`（1箇所）は**性質が違う**。高さの補間は毎フレーム再レイアウトを起こし、
  結果パネルの中身（EVルーラー・警告リスト）を巻き込む。**修正対象。**
  ただし `transform: scaleY` で置き換えると中身が歪むため、素直な直し方は
  **遷移を外して即時に切り替える**こと。見た目が変わるので §5 に載せる

### C. 4px リズムからの逸脱（違反・**未修正**）

UI仕様 §7 は `4 / 8 / 12 / 16 / 24 / 32` のみ。実際に使われている非準拠値：

| 値 | 箇所数 | 例 |
| --- | --- | --- |
| `6px` | 10 | `gap`（`:113,121,143,173,343,379`）、`margin-top`（`:148`）、`margin-bottom`（`:347`）、`padding`（`:373`） |
| `10px` | 4 | `padding: 0 10px`（`:114`）、`padding: 8px 10px`（`:362,391`）、`padding: 10px 16px`（`:428`） |
| `14px` | 1 | `padding: 0 14px`（`:172`） |
| `2px` | 4 | `margin`（`:182,369,531`）、`padding: 2px 8px`（`:227`） |
| `26px` | 1 | `height`（`:347`） |

**判断：修正しない（現状を記録する）。**

理由：`6px` の `gap` はアイコンと文字の間隔、`10px` / `14px` はチップの左右パディングで、
**44px の当たり判定を保ちながら文字幅に合わせた値**になっている。4の倍数に丸めると
チップの幅とタップ間隔が全体で変わり、**320px 幅での折り返し（項目15）を作り直すことになる。**
リズムの目的（余白の乱雑さを防ぐ）は「値の種類が7つに収まっている」ことで達たしている。

`2px` は境界線・下線オフセット・負マージンの微調整で、余白ではない。

→ **MAINTENANCE.md §12 に「4px リズムの実運用は 2/6/10/14 を含む」として記録する。**
仕様 §7 の文言を実装に合わせるほうが正しいが、仕様書は正典なので勝手に書き換えない。

### D. 結果パネルの `aria-live` 抑制（未実装・**未修正**）

UI仕様 §13：「`aria-live="polite"` で値の変化を読み上げる。ただし**連続変更中は抑制**し、
確定後に1回だけ」。

現状：`index.html:232`（`result-summary`）と `:240`（`result-systems`）に
`aria-live="polite"` があるが、抑制の仕組みが無い。

**連続変更が起きる入力：**

| 入力 | イベント | 連続するか |
| --- | --- | --- |
| シーン微調整スライダー | `input` | **する**（1/3段ごとに `setState`） |
| ホイールピッカー | `onCommit`（指を離したとき） | しない |
| チップ・タイル | `click` | しない |

**判断：修正する。ただし実装は次工程。**
`aria-busy="true"` をスライダーの `pointerdown`〜`change` の間だけ立てるのが定石だが、
**スクリーンリーダーでの実挙動を確認せずに入れると「確定後に1回」が本当に鳴るか分からない。**
コードだけで正しさを主張できないので、§5 に「実装＋VoiceOver 確認」として載せる。

なお `role="alert"` / `role="status"` の使い分け（§13）も未実装：
`index.html:242` の警告コンテナは `role="status"` 固定で、`alert` レベルでも `status`。
入れ子のライブリージョンは二重発話を招くため、これも実機確認とセットで行う。

## 8.1 ホイールのワープ（実機で再現手順が判明）— 追記

### 原因は2つが重なっていた

再現手順（横スワイプ中に縦スクロールが挟まる）どおりに追ったところ、
**`pointercancel` が `endDrag`（＝確定処理）に繋がっていた**のが直接の原因でした。

```js
// 修正前（js/wheel.js:100-101）
root.addEventListener('pointerup', endDrag);
root.addEventListener('pointercancel', endDrag);   // ← キャンセルでも値を確定していた
```

`endDrag` は「最後に分かっている `clientX`」から値を計算して `onCommit` します。
スクロールが始まってブラウザがタッチを引き取ると `pointercancel` が飛び、**ユーザーが
選んでいない値が確定**されました。**確定した値が次のジェスチャの起点（`index`）になるため、
繰り返すと悪化します。** PC で再現しないのはマウスドラッグがスクロールと競合しないため
——ご指摘の見立てのとおりです。

`touch-action` については、`.wheel` に `pan-y` が**既に書かれていました**が、
読み取り専用のホイール（結果パネル側）にも一律で当たっていました。

### ① `touch-action` — 付けた要素と付けなかった要素

| 要素 | 指定 | 判断 |
| --- | --- | --- |
| `.wheel:not(.is-readonly)`（操作するホイール） | **`pan-y`** | 横はアプリ、縦はページのスクロールへ。`none` にすると**計算タブは画面の大半がホイールなので縦スクロールができず操作不能**になる |
| `.wheel.is-readonly`（結果パネルのトラック） | **付けない** | 入力を受け付けないので競合しない。害はないが「ここは操作する要素」という意図を1行で表すため分けた（ご指示どおり） |
| `.scroll-body`（親のスクロールコンテナ） | **付けない** | 範囲を広げるとページ全体のスクロールが壊れる |
| `.panel-handle` | `none`（既存・維持） | **縦スワイプそのものが操作**なので、縦を渡してはいけない。ホイールとは要件が逆 |

### ② `touchcancel` / `pointercancel` — 値は**開始時に戻す**

**その時点の値で止めるのではなく、開始時の値へ戻しました。** 理由：

- キャンセルはシステム都合の中断（スクロール・電話着信・通知・システムジェスチャ）で、
  **ユーザーの操作が完了した合図ではない**
- 中途の値を残すと「選んだつもりのない設定で撮る」ことになる。露出はやり直しが効かない
- やり直しは指を置き直すだけなので、戻すコストは小さい

実装は `place(true)` の1行です（`index` はドラッグ中に触っていないので、これが開始時の位置）。
この判断の理由は `js/wheel.js` の `pointercancel` のコメントに、症状ごと記録しました。

**同じ欠落が他に2箇所ありました**（新しい不変条件に照らして洗い出したもの）。

| 箇所 | 欠けていたもの | 起きうる症状 |
| --- | --- | --- |
| `.panel-handle`（結果パネルの高さ変更） | `touchcancel` | `moved` が `true` のまま残り、**次のタップが「スワイプ直後」と誤判定されて無視される** |
| `#manual`（マニュアルの横／下スワイプ） | `touchcancel` | `touch` が残る。次の `touchstart` が上書きするので実害は小さいが、開始点の取り違えの余地が残る |

どちらも「状態を捨てるだけ・値は確定しない」で統一しました。

### ③ 構造 — `indexFromDrag` を純粋関数に切り出した

```js
export function indexFromDrag(startIndex, totalDxPx, stepPx, len)  // → 0..len-1 の整数
```

ジェスチャの状態も**1つのオブジェクトに閉じました**（`drag = { pointerId, startX, startIndex }`）。
個別の変数に散らすと、どれか1つを消し忘れて前のジェスチャが持ち越されます。

- `pointerdown` で毎回作り直す（`startIndex` は現在値から取り直す）
- ドラッグ中に新しい `pointerdown` が来たら前を破棄して始める
- `pointermove` / `pointerup` / `pointercancel` は **`pointerId` が一致するイベントだけ**扱う
  （2本目の指のイベントで進行中のドラッグを壊さない）

`totalDxPx` は**正でインデックスが増える向き**と定義し、呼び出し側が `startX − currentX` を
渡します（ホイールは指を左へ動かすと値が上がる）。座標系の取り違えを引数の定義で封じる形です。

### 採らない案の記録

「1秒以上停止したらスクロールを許可する」案を採らない理由（遅延が体感を悪くする／判定の条件が
増えて別の不具合を生む／`touch-action` は宣言1行でブラウザ側が処理する）を
**UI仕様 §3 の「採らない案：停止時間による判定」**として記録しました。

### 文書

| 文書 | 追記した内容 |
| --- | --- |
| `docs/exposure-app-ui-spec.md` §3 | `touch-action: pan-y` の指定、**なぜ `none` ではないか**、読み取り専用と親コンテナに付けない理由、実機で起きた症状の記録、採らない案 |
| `docs/MAINTENANCE.md` §4（不変条件） | 「タッチで操作する要素には `touch-action` を宣言し、`touchcancel` を必ず処理する。どちらか欠けるとスクロールとの競合で状態が壊れる」＋守るべき5点の節 |
| `js/wheel.js` | `pointercancel` のコメントに症状と「値を確定しない／開始時に戻す」判断 |
