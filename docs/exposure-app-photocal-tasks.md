## フェーズ0：EXIF が読めるかの検証

> 目的は、実装前に**機能A と機能B が成立するかを確かめる**こと。
> iOS の写真アプリ経由でファイルを選んだとき EXIF が残るかが未知で、
> 失われると数百行が無駄になる。先に30分で確かめる。

### 渡す指示

```
新機能の検討に入ります。実装の前に検証を1つお願いします。

docs/exposure-app-photocal-spec.md を追加しました。
§1・§2・§6・§9.1 を読んでから着手してください。

■ 背景

  スマホで撮った写真の EXIF から F値・SS・ISO が取れれば、
  そこからシーンEV を逆算できます。つまりスマホが露出計になります。
  日中シンクロはシーンEV の精度がそのまま背景の明るさに出るので、
  現在の「シーンチップ＋微調整スライダー」を実測に置き換えられます。

  カメラの写真からストロボ校正の入力を埋める機能も同じ仕組みで作れます。

  ただし iOS の写真アプリ経由でファイルを選択したとき、
  EXIF が保持されるか再エンコードで失われるかが分かっていません。
  両機能がここに依存するので先に確かめます。

■ 作ってほしいもの

  tools/exif-probe.html

  使い捨ての検証ページです。以下の要件で作ってください。

  - ファイル選択ボタン1つ（accept は指定しない。何でも選べるように）
  - 選択されたファイルについて、以下を画面にそのまま表示する

      File.name / File.type / File.size
      先頭32バイトの16進ダンプ
      JPEG なら APP1 セグメントが見つかったか（オフセットと長さ）
      APP1 内に "Exif\0\0" があるか
      TIFF ヘッダのバイトオーダー（II / MM）
      IFD0 と ExifIFD で見つかったタグ番号の一覧（16進）
      主要タグの生の値
        0x829D FNumber / 0x829A ExposureTime / 0x8827 ISO /
        0x920A FocalLength / 0x9209 Flash /
        0x010F Make / 0x0110 Model / 0x9003 DateTimeOriginal
      HEIC なら ftyp のブランドと、meta / iinf / iloc の有無

  - 加えて、読めた F/SS/ISO から EV を計算して表示してください

      EV(ISO100基準) = log2(N² / t) − log2(S / 100)

    これが露出計の中核の式です。ここで妥当な値が出るかを見たいです。
    検算用：F16 / 1/125 / ISO100 なら EV = 15.0（サニー16）になります。

  - パースに失敗しても例外で止まらず、どこまで進めたかを表示すること
  - GPS タグ（0x8825）は「存在した／しなかった」だけを表示し、
    中身は読まないこと（仕様書 §6.5）

■ 制約

  - ASSETS に追加しないこと（配布対象外・開発用）
  - tools/check-sw-assets の除外リストに tools/ が入っているか確認
  - 外部ライブラリを使わないこと
  - js/ 以下のファイルを一切変更しないこと
  - sw.js も CACHE も触らないこと

■ 報告

  - tools/exif-probe.html を作ったこと
  - tools/check-sw-assets が exit 0 のままであること
  - サニー16（F16 / 1/125 / ISO100 → EV15.0）で検算した結果
  - 私が実機で確認する手順
```

### 検証（人がやる）

```
  export function parseExif(buf)   // ArrayBuffer → 値オブジェクト | null

■ 守ること

  - DOM・Canvas・fetch・localStorage に触らないこと
  - 読めなければ null を返し、例外を投げないこと
  - リトルエンディアン（II）とビッグエンディアン（MM）の両方に対応
  - GPS タグ（0x8825）を読まないこと。除外を意図的に行い、
    その旨をコメントに書くこと（仕様書 §6.5）
  - 外部ライブラリを使わないこと

■ 読むタグ（これだけ）

  0x829D FNumber          → number（有理数を除算して実数に）
  0x829A ExposureTime     → number（秒。1/250 なら 0.004）
  0x8827 ISOSpeedRatings  → number
  0x920A FocalLength      → number
  0x9209 Flash            → boolean（bit 0 が発光の有無）
  0x010F Make             → string
  0x0110 Model            → string
  0x9003 DateTimeOriginal → string

■ HEIC

  フェーズ0 で HEIC が渡された場合、format: 'heic' を返して
  他は null にしてください。BMFF パースは後回しです。

  UI 側で「設定 → カメラ → フォーマット → 互換性優先 に
  変更してください」と案内します（仕様書 §6.2）。

■ ② js/lightmeter.js（純粋関数）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

仕様書 §7.2 のシグネチャで実装してください。

  export function evFromExposure({ fNumber, exposureTime, iso }, aeOffsetStops)
  export function solveAeOffset(phoneExposure, cameraExposure)

■ 式

  EV(ISO100基準) = log2(N² / t) − log2(S / 100) + aeOffsetStops

  検算：F16 / 1/125 / ISO100 / オフセット0 → EV = 15.0（サニー16）
        log2(256 × 125) = log2(32000) = 14.966

■ 守ること

  - 純粋関数。副作用を持たないこと
  - ExposureTime が 0 のときゼロ除算を起こさないこと
  - 値が欠損しているときは ev: null と理由を返すこと
  - ナイトモードの疑いを検出すること
    （SS が 1秒以上 かつ ISO が 3200以上 なら suspectNightMode: true）
```

## フェーズ2：カメラの EXIF で校正入力を補完


## フェーズ3：白飛び警告（測らない方式）

> **単独で実装できる。フェーズ0〜2 と独立。先に入れてもよい。**
> 20〜30行で、日中シンクロの実運用課題に効く。

### 渡す指示

```
日中シンクロで背景が白飛びする問題に対応してください。
仕様書 §5.1・§5.2・§5.4 が該当箇所です。

写真を使わない方式です。既存の情報だけで警告が出せます。

■ 何が問題か

  背景が飛ぶ原因は3つあります。

    シーンEV の見積もり違い      → 別途フェーズ1 で対応
    背景段数の選択が明るすぎる    → 選択は自由なので警告は不要
    シーンのダイナミックレンジが  → ここを判定していない
    センサーを超える

  3つ目が本質です。適正露出でも空は飛びます。
  中間調から上のヘッドルームは JPEG で約3段しかないため、
  晴天の空が被写体より4段明るければ、被写体を適正にした時点で飛びます。

■ 実装

  1. scenes.js にシーン別のコントラスト目安を追加

     快晴・順光          2.5段
     快晴・逆光          4.5段
     晴れ・薄曇り        2.0段
     晴れ・日陰の被写体  4.0段
     曇り                1.5段
     厚い曇り／日陰      1.0段
     日没直後            2.0段

     これは「空（または最も明るい背景）が被写体より何段明るいか」の目安です。
     推定値であることを明示してください。

  2. カメラのヘッドルームを設定に追加

     camera.highlightHeadroomStops（既定 3.0）
     設定タブで 2.0〜4.5 の範囲で調整可能に。

     JPEG は約3段、RAW なら 3.5〜4段です。
     ユーザーが実機で調整できるようにします。

  3. 判定と警告

     オーバー段数 = コントラスト目安 + 背景段数 − ヘッドルーム
     これが正なら警告。

■ 警告の出し方（重要）

  段数そのものを見せるより、選ぶべき背景段数を出してください。
  誤差に強く、そのまま行動に移せます。

    空が飛ぶ可能性があります（快晴・逆光の目安：4.5段）

      背景 0段   → 約 1.5段 オーバー
      背景 −1段  → 約 0.5段 オーバー
      背景 −2段  → 空が残ります   ← 推奨

    ※ 空を飛ばす表現を狙う場合はこの警告を無視してかまいません

  最後の一文を必ず入れてください。意図的に飛ばす表現もあるためです。

■ 受け入れテスト2件

  C1  快晴・逆光（4.5段）/ 背景0段 / ヘッドルーム3.0
      → 1.5段オーバーの警告が出て、推奨背景段数が −2段になること

  C2  曇り（1.5段）/ 背景−1段 / ヘッドルーム3.0
      → 警告が出ないこと（1.5 + (−1) − 3.0 = −2.5 で余裕がある）

■ helpId

  新しい警告に helpId を割り当て、マニュアル §0.5 の対応表に追加。
  対応するセクションをマニュアル本文に新設してください
  （「空が飛ぶのを防ぐ」など）。日中シンクロの節と関連付けること。

■ 文書

  1. docs/exposure-app-spec.md にコントラスト目安の表とヘッドルームの仕様
  2. docs/exposure-app-manual.md に新設セクション
  3. docs/exposure-app-manual.md §0.5 と index.html（helpId）
```

## フェーズ4：白飛びの測定（任意）

> **フェーズ3 を実際に使って不足を感じた場合のみ。**
> 測定は ±1.5段の目安で、表方式（±1段程度）と大差ない可能性がある。

### 渡す指示

```
フェーズ4 に進みます。仕様書 §5.2・§5.3・§7.3・§8.4 が該当箇所です。

■ 位置づけ

  写真の画素値から「空が被写体より何段明るいか」を測ります。
  HDR のトーンマッピングで空が圧縮されるため精度は ±1.5段です。

  条件を満たさないときは測定せず、理由を出してください。
  「近い値を出す」ことより「測れないと言う」ことを優先します。

■ ① js/photometry.js（純粋関数）

  仕様書 §7.3 のシグネチャ、§5.3 のアルゴリズムで実装してください。

  - ImageData そのものではなく { width, height, data } を受け取ること
    （テストで合成データを渡せるようにするため）
  - DOM・Canvas に触らないこと
  - sRGB の線形化は区分関数を使うこと（単純な 2.2 乗にしない）

      v = V / 255
      linear = v <= 0.04045 ? v / 12.92 : ((v + 0.055) / 1.055) ** 2.4

  - 輝度係数は 0.2126 / 0.7152 / 0.0722
  - 18%グレー（線形 0.18）を基準に log2 で段数化

  ■ 信頼性の判定

    以下のいずれかで reliable: false とし、理由を返してください。

      飽和画素（V ≥ 250）が範囲の 2% 超
      黒潰れ画素（V ≤ 5）が範囲の 2% 超
      |stops| > 1.5
      範囲内の標準偏差が大きい（閾値は実装判断。根拠をコメントに）

    reliable: false のとき stops は null。

■ ② テスト P1〜P8

  仕様書 §8.4 のとおり。合成 ImageData で検証してください。
  P1〜P3 の期待値は仕様書 §5.3 の表から導出しています。検算すること。

■ ③ UI（オプトイン）

  既定でオフ。

    □ 写真から空の明るさを測る

  オンにするとプレビューが出て、被写体と空をそれぞれタップして
  もらい、差を測ります。

  - 長辺 256px に縮小して Canvas に描画（巨大な画像で固まらないため）
  - 測定結果はフェーズ3 と同じ形式で出す
    （推奨背景段数を提示。段数そのものより行動を出す）
```
